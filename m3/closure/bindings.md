# M3-08 closure: harness bindings and transformations

**Status:** implementation of D-037 items 1, 2, 3, 5, 6 and 7 (with the D-038 item 2 to 4 companions, section 6) in the closure adapter (`persistence/sqlite/examples/m3_line_adapter/`, a non-shipping Cargo example). Every transformation between a frozen M1 fixture and the production broker's inputs is listed here. Frozen fixtures (`m1/`) are never changed. Test keys, test sources, test authorities and harness bundles are test infrastructure only; they do not establish production authentication, key provisioning, the acceptance service, the runner or the immutable snapshot store (M4 to M6). Seeded transition cases are **production-component tests with synthetic preconditions**.

## 1. Harness authorization bundles (D-037 item 2)

Files in `m3/closure/bundles/`, derived from `m1/fixtures/transition/m1-transition.bundle.json`: scope `t1/p1`, trusted issuer `writ-host-adapter:fixture`, the original `workflow_protection` (except where stated), and only the statements the scenarios that use the bundle need. Each is loaded through the production `load_bundle`; its digest is computed at run time and never asserted (digests below are informational, D-006 over the file without `publisher_signature`).

**Declared per-case table.** `m3/closure/bundles/cases.json` (the machine copy of the table below, read by the adapter) names, per case id, the active bundle, the bundle `activate_authorization_bundle` activates, an optional trusted-record override (`records_from`) and an optional runner-outcome override (`runner`; none is used). The choice follows what each scenario does according to its documented intent (SCENARIOS.md and the case rationale), **never the fixture's client permits**, which the adapter does not read. A case id that is not listed is refused at setup (`refused_setup`). Cases whose input is refused before setup (sc-48, sc-49, p-04) need no entry.

Notes on the scoping:

- `accept-deploy` (sc-03, sc-04, sc-17): the second transition of sc-03 and sc-04 and the target of sc-17 is `deployed`; the original `require_approval` becomes `permit` because the transition scenarios model no approval grants. No other bundle authorizes `deployed`.
- sc-18 ("permit issued for to_state accepted presented with to_state deployed") runs under `accept`: the scenario authorizes only verifying to accepted, so its deployed request is `DEFAULT_DENY`.
- sc-42 and sc-45 run under `publish-other`: their second request (to `repository:t1/p1/other`) is a legitimate distinct request whose authorization the scenario assumes (sc-45 expects it to complete; sc-42 tests the key binding, which a policy denial would mask). sc-62 ("a publication permit cannot be reused for another target") runs under `publish`: the scenario authorizes publication to releases only, so the request to `other` is `DEFAULT_DENY` with zero effects. These three outcomes are unchanged from the previous revision, now derived from the table.
- `protection-only` authorizes nothing (sc-47 and p-08 need no action; companion m3c-09; replacement bundle of companion m3c-36). `protection-missing` is rejected by production `load_bundle` (transition support without protection); the broker then runs with a rejected policy (companion m3c-50). `accept-release-manager` restricts acceptance to role `release-manager` (companion m3c-19). `accept-e` and `accept-publish-e` carry protection compatible with acceptance-policy bundle `sha256:eeee...`.
- **Activation:** `activate_authorization_bundle {authorization_bundle_sha, protection}` activates the declared bundle through the trusted `ActivePolicy::activate`, only if its `workflow_protection` equals the step's `protection` and its computed digest differs from the active one; otherwise `unsupported` (none occurs). The step's bare digest (`sha256:9999...`) is never policy authority.
- No broad allow-all bundle; wrong scope, missing policy, default deny and activation invalidation stay covered by the production policy tests and the broker scenarios (b-19, b-39).

## 3. Authenticated test evidence (D-037 item 3)

- **Keys:** acceptance-record key `m3c-acceptance-key-1` (type `AcceptanceRecordKey`) and runner key `runner-key-1` (type `RunnerAttestationKey`), distinct purposes and values; HMAC-SHA256 computed in the example from the kernel's SHA-256 (no new dependency). HMAC is a MAC, not a signature.
- **Registry:** four `evaluator-registry-entry/1` entries scoped to the case's tenant and project, registered through production `administer(RegisterEvaluator)`: `ci-runner` (mechanical, M, command `cargo-test`, criterion `build`), `evidence-engine` (evidence, E, `citations`), `approval-service` (human, H, `signoff`), `reviewer-model` (model_assisted, MA, `style`); version `1.4.0`, implementation and environment digests `sha256:1111...`, `sha256:2222...`, registry revision 12, attestation key `runner-key-1`. They are the registry's standing contents, not derived from any record or expectation.
- **Record issuance (once, at setup):** for each record id the test source issues exactly one record before step 0: the declared `records_from` override if any, otherwise the **first** inline presentation of that id in the case. A later inline record with an already issued id is never MACed into the trusted source. Overrides (cases.json): **sc-12** holds the complete record of step 1, the step expected to commit: that is the record the acceptance service would issue for acc-1; the agent's step-0 inline record (build evaluator trust MA) is a non-authoritative claim (D-036 item 1, D-037 item 3) and never decides what the source holds. **sc-25** holds the original record of sc-01 step 0, which the scenario says the swapped record replaces; its swapped inline record is never issued. Companion m3c-25 uses m3c-01 step 0.
- **Record translation:** `authenticated-acceptance-record/1` with `record` = the fixture record **unchanged** (no repair, its own `record_digest`), `issuer` `m3c-test-acceptance-service`, `mode` governed, and one evaluation per record criterion whose evaluator is registered: `evaluation_id` `eval-<record>-<criterion>`, the registered evaluator binding, `attestation_id` `att-<record>-<criterion>` exactly for evaluator trust `M` (else null), no evidence digests. The source does not filter by tenant or project, so production's own scope check runs (sc-16). A semantically defective record (sc-12, sc-14, sc-16, sc-26, sc-29) still gets a valid test MAC because semantic validation is under test; no fixture case tests an invalid record MAC, so no tamper-after-MAC case arises (the broker permit tamper cases b-09, b-13 tamper after the MAC).
- **Synthetic attestations** (one per trust-`M` criterion of an issued record): bound to the record's context (tenant, project, task, workflow, transition, snapshot and digest, `workflow:<t>/<p>/<w>` target, acceptance policy id, version and digest, state revision, record id), the criterion, the registered evaluator binding and command; MACed with `runner-key-1`. The **run outcome is the declared harness runner outcome** (`cases.json` `runner_default`: `exit_status` 0, started `2026-11-07T10:58:00Z`, finished `10:59:00Z`, fresh until `11:30:00Z`; a per-case `runner` override, none used), never the record's own criterion status or times. They test verification only; end-to-end runner-produced attestation coverage stays with the runner tests (M3-07).
- **Snapshot store:** confirms exactly the (snapshot id, digest) pairs the scenario declares: the initial artifact, the artifact of `last_promotion`, and each `update_artifact`. A record naming any other pair is `ARTIFACT_INTEGRITY_VIOLATION` (INV-40; sc-26, an exact D-038 item 4 difference: `snap-2` is never added to the store for sc-26). Companion m3c-26 declares `snap-2` as trusted through its seeded `last_promotion` (a declared precondition), so its record passes the integrity check and reaches the binding check.

## 4. Preconditions (D-037 item 1, I-2)

Order: production `SqliteLedger::create` and `SqliteEffectStore::create`; production administration (registry, revocations, acceptance policy and, when the initial state is neither protected nor the target of a protected edge and there is no `last_promotion`, `CreateWorkflow` plus `revision` artifact updates); then every store is closed and the test seeder writes, in one rusqlite transaction, only what production cannot express:

- the workflow row in a protected state (or with history) at the fixture revision, with the `last_promotion` columns;
- for `last_promotion`: a promotion receipt (`idempotency_key` `m3c-seed-<receipt id>`, fingerprint the D-006 digest of `{"m3c_seeded_promotion": <receipt id>}`, revision parsed from the receipt id) and a `promote` workflow event (`from_state` null, the fixture does not say);
- every `consumed_record_ids` entry (the last promotion's record under the seed promotion key, others under `m3c-seed-consumed-<id>`).

Then validation on the closed ledger, failing closed with `{"refused_setup": {"case", "reason"}}` without running the case: the state is a state named by the active bundle; revision at least 1 and at least the number of revision-changing workflow events (`artifact`, `promote`; the production `create` event is at revision 0 and is not counted); the last-promotion columns all or none, its receipt belongs to this workflow at a revision between 1 and the current one, matches `promotion:<workflow>:<revision>`, has its `promote` event with the record, and its record is consumed; consumed records equal `consumed_record_ids`; revoked evaluators equal `revoked_evaluator_ids`; no receipt exists for any step's idempotency key and no consumed record is presented by any step. Then production `open` for both stores and a new broker. Negative tests: `m3/closure/companions/seed-negatives.jsonl` (6 cases, all refused). Production itself still cannot create protected initial states (`WORKFLOW_INITIAL_STATE_PROTECTED`, `transition_tests`).

## 5. Inspection (D-037 item 7)

Final state is read through read-only connections only after the case closes every store (no owner, quiescent); seeding opens a read-write connection only while every store is closed. The adapter refuses either while a store is open.

## 6. Companions (D-037 item 4, I-5)

`m3/closure/companions/transition-companions.jsonl`: 27 mechanical-only companion cases (`meta.label` "mechanical-only companion; not human-signoff coverage", `meta.companion_of` the frozen case, `meta.invariant` the invariant). Inputs are the frozen inputs with the requirement sets (initial and `activate_policy`) reduced to the mechanical criterion `build` and inline records reduced to `build` plus the non-mandatory `style` (record digest recomputed). m3c-12, m3c-13 and m3c-38 present the refused (untrusted-evaluator) record under its own id `acc-0`, because a record id is issued once. Companions of the cases where the human criterion refuses first although the frozen case targets another invariant: m3c-09 (a transition the policy does not allow, `protection-only`), m3c-19 (authorization follows the presented actor, `accept-release-manager`), m3c-25 (an inline swapped record is never authority), m3c-36 (a superseded bundle never authorizes), m3c-50 (a bundle without protection is rejected at load, `POLICY_BUNDLE_REJECTED`), m3c-51 (an inconsistent policy view fails closed, `POLICY_DEPENDENCY_MISMATCH`). Companions added for D-038: m3c-10 (sc-10, replaces the former waiver: 16 concurrent mechanical promotions with distinct keys and one record; exactly one commits, 15 answer `REVISION_CONFLICT`, D-038 item 2, the record is consumed once; the adapter's concurrent answer is the aggregate `{committed, refused: {code: count}}`, compared exactly, so the winning thread may vary), m3c-26 (sc-26: two declared trusted snapshots, `snap-1` current and `snap-2` from a seeded earlier promotion `promotion:wf-1:6` with record `acc-0`; request attributes name `snap-1`, the record `snap-2`; `PERMIT_BINDING_MISMATCH`, nothing changes, D-038 item 4) and m3c-27 (sc-27: a request scoped to `t1/p1` whose resource names `workflow:t1/p2/wf-1` is a real scope violation, `REQUEST_SCOPE_MISMATCH`, never `WORKFLOW_UNKNOWN`, D-038 item 3). Expectations are written by hand from the invariant, never copied from adapter output.

`m3/closure/companions/seed-negatives.jsonl`: 6 inconsistent seeds, each refused at setup.
