## Behavioral slices

Acceptance cases below specify what the implementation must execute and assert. Run schema fixtures with `python3 scripts/check-v2-docs.py` and `python3 -m unittest discover -s docs/contracts/proposed`. Run behavioral fixtures with `m3/tools/run-with-clean-fds.sh cargo test --workspace --locked`. Run the existing parity, property and closure gates wherever shared path integration changes. Each negative case checks that authority, durable state and effects advance only as explicitly expected.

### 1. Compile and prove a synthetic rule offline

**First batch.** Depends on decision 1 and the accepted kernel interfaces. No verified host integration is required. Deliver a local invocation with fixture inputs and a deterministic compile, validation, conflict, fixture and enforcement-binding report. Start with one narrowly scoped, non-transition synthetic V2 action family. Give each PolicyManifest a closed, versioned companion entry keyed by policy ID and version. The entry supplies effect, reason code and canonical resource prefix. Derive tenant and action kind from the manifest, and use stable statement IDs. Use the real kernel decision path in tests. The report identifies the manifest and exact compiled statement and fixture set and distinguishes local proof from deployed enforcement.

- Compile the same inputs twice and with equivalent input order. Require identical canonical bytes, digest and diagnostics. Load the output through the existing kernel loader. Compare exact decisions for matching, out-of-scope and unknown cases with the frozen expected results. Run a matching permit alone, then with a matching approval, then with a matching hard deny. Assert `allow`, `require_approval` and `deny` respectively with exact winning reasons and matched statement IDs.
- Refuse malformed and duplicate manifests, unsupported selectors, same-tier overlaps with different reason codes, including different manifest priorities, missing or stale binding or test evidence, failing negative fixtures, and advisory or unreviewed legacy additions to an enforced candidate. Remove the registered implementation in a test and require the report to mark it `UNVERIFIED` and refuse the candidate (INV-20, CC-SEC-18).
- Run the report and validation without opening a broker, executing effects or writing active state. The batch finishes at the offline artifact and reproducible tests, before signing or publication.

### 2. Publish, verify and select signed policy with test authorities

Depends on slice 1, decision 2 and the existing policy requirements and activation interfaces. Deliver an in-process or disposable-store lifecycle from validated draft through authenticated publication, verified load and test-only selection. Guard both authorization and acceptance payloads. Commit the new selection and required audit coherently, preserving immutable publication history.

- Publish an exact validated revision with a fresh scoped human publisher and reload it using only public verification material. Exercise signature, scope, payload and compatibility checks with valid fixtures. Refuse byte changes, missing or invalid signatures, unknown or revoked keys, expired metadata, stale validation evidence, direct unauthorized publication and protected policy weakening.
- Race two expected-revision selections and prove at most one commits. Inject audit or store failure and restart before or after commit to verify a coherent previous or new selection with durable audit. Race activation against grant consumption and effect dispatch with a test adapter. Assert the existing fence order, no dispatch under a stale permit and no extra grant consumption. Verify ordinary approvals and acceptance records still follow their existing exact policy binding rules. Carry no policy-equivalence exception into this contract.
- Refuse a replayed or downgraded selection. An explicit rollback revalidates the previous immutable publication against current trust and mandatory policy, appends a higher activation revision, and keeps history. Reject a retired, revoked or tampered target, partial pairs, and individually valid authorization and acceptance payloads that were never approved together with those prerequisites (AG-ADV-09/10, CC-SEC-04/12).

### 3. Publish and revoke an evaluator and bind a pack rubric

Depends on slice 2's publisher authorization and audit path and D-034's evaluator contract. Deliver a test-authority publication and revocation path and a rubric validation result. Reuse the semantic RegistryEntry validator, trusted workflow reads and registered command digests for the integration fixture. Extend the current register-only revision advance to revocation, with durable status and provenance in the same transaction.

- Publish a scoped test evaluator, advance the registry revision, bind a proposed rubric to that exact version and criteria, and use an authenticated acceptance fixture against the resulting view. Refuse stale edits, unknown or wrong-scope entries, class or criterion mismatches, key or implementation mismatch, and attempts by agents or packs to publish evaluators or raise their trust.
- Revoke an evaluator or its key and refuse the previously usable record at use time. Race revocation with promotion and assert the outcome follows the existing fence and durable revision order. A refused promotion does not advance workflow state or consume evidence. Registry outage and failed audit refuse the dependent operation (AG-ADV-16).
- Enable, disable and upgrade a fixture pack. Compare authorization decisions across the golden corpus and assert zero permission changes. Invalid or unregistered rubric bindings cannot satisfy mandatory requirements (CC-SEC-16).

### 4. Record a waiver through scoped human approval

Depends on slices 2 and 3, decision 3 and M4 human approval provenance. Deliver the request, approval, recording and use-time check for one synthetic policy criterion with test authorities.

- For a criterion explicitly marked waivable, use a fresh authorized human approval bound to the exact criterion, artifact snapshot and digest, policy, workflow, transition, tenant, project, task, revision, requester and expiry. Persist an audited `waived` result with approver, reason and grant reference. Under current kernel semantics a mandatory criterion remains incomplete and promotion is refused (AG-POS-02).
- Refuse invariant-derived or undeclared criteria, forged or self-approved waivers, stale or replayed approvals, changed bindings, revocation and unavailable authority or audit. Verify no waiver satisfies an ordinary effect grant, human signoff or hard-denied transition. Verify duplicate and concurrent submissions can commit at most one waiver record and consumption.
