## J-1 Process and privilege model (revision 4: BINDING; D-046 C-1, H-2)

**Identities (D-046 C-1, H-2).** Five principals with pairwise distinct uids; none is a member of another's group except as listed.

| Identity | Account | Groups | Runs | Never |
|---|---|---|---|---|
| Human desktop and browser user | the person's login uid, configured as `desktop_uids` | own primary group only; never `writ`, `writ-agents` or `writ-job` | the desktop session, the browser that displays the approval page, the authenticators | an agent uid; any Writ service |
| Agent | dedicated account, default `writ-agent` (one or more configured agent uids); own home, login shell allowed | primary group of its own; supplementary `writ-agents` **only** | the agent host (Claude Code in M5b), the hook client, the MCP shim, the CLI client; its model credential lives in its own home (M5-D12) | the human's uid; any group listed in P-AGENT-DENY |
| Service | `writ` system account, no login shell, home `/var/lib/writ` | primary `writ`, no supplementary groups | `writ-serviced` (`writ.service`) | job processes; membership of `writ-agents` or `writ-job` |
| Job | `writ-job` system account, no login shell, home `/nonexistent` | primary `writ-job`, **no supplementary groups**, no other member of `writ-job` | runner jobs only, created by the launcher (J-11) | access to Writ state, keys, sockets, the human's files or cgroup controls |
| Root | operator procedures on the disposable reference host (M5-D3); the job launcher (J-11) | | install, provisioning, teardown, `admin.sock` operations (J-11.8), job establishment | running any part of the agent |

**Static identity check** (at `writ-serviced` start, at every readiness recheck, and in the probes): the configured agent, job and desktop uids are pairwise distinct and none is 0 or the `writ` uid; group `writ` has no member accounts (the launcher unit receives it through `SupplementaryGroups=writ`, J-11.2); `writ-agents` contains exactly the configured agent uids; `writ-job` has no supplementary groups and its group has no other member; no desktop uid is in `writ`, `writ-agents` or `writ-job`; no agent uid or `writ-job` is in a desktop uid's primary group; `writ` is in no supplementary group. A violation withdraws `VerifiedDeployment` (J-9).

**Agent denial requirements (C-1).** The agent uid cannot:

1. **Home and browser profile:** read, list or write the human's home directory, including browser profiles (Firefox, Chromium and Chrome profiles, snap-packaged browser directories under `~/snap`). The approval page's cookies, session storage and any cached page content exist only there; the approval server never writes a session token or cookie to any other file.
2. **Display:** reach the human's display server: X11 sockets `/tmp/.X11-unix/X*` and the abstract `@/tmp/.X11-unix/X*` (an abstract socket may accept the connection, so the requirement is that X11 authorization refuses the agent uid: no `xhost` local-user, wildcard or family grant, and the human's `.Xauthority` is unreadable), Wayland sockets in the human's `$XDG_RUNTIME_DIR`, and Xwayland. Consequently no input injection, screen capture, clipboard access or window manipulation.
3. **Session bus and runtime directory:** reach `/run/user/<human uid>` at all (mode 0700), and therefore the session bus, portals, PipeWire and PulseAudio sockets in it.
4. **Authentication state:** reach secret-service or keyring daemons (gnome-keyring control socket, KWallet), the human's kernel keyrings, `ssh-agent` and `gpg-agent` sockets (in `$XDG_RUNTIME_DIR/keyring/`, `$XDG_RUNTIME_DIR/gnupg/`, `/tmp/ssh-*/`), the polkit authentication agent of the human's session, FIDO authenticators (`/dev/hidraw*` with the seat user's `uaccess` ACL) and platform passkeys (held by the human's browser or OS credential store). Agent processes are never members of the human's logind session, so polkit has no authentication agent through which to prompt the human; administrative polkit actions requested by the agent answer "not authorized" without a challenge.
5. **Processes:** trace, signal or read `/proc/<pid>/environ` of the human's processes (different uid; `kernel.yama.ptrace_scope >= 1`).
6. **Terminal:** share a terminal with the human. The agent is started in its own login session and pseudo-terminal (`machinectl shell writ-agent@`, `systemd-run --uid=writ-agent --pty`, or SSH to the agent account), never by `sudo` or `su` from the human's terminal; `dev.tty.legacy_tiocsti = 0` so `TIOCSTI` cannot inject input.

Each item is verified by **P-AGENT-DESKTOP** (J-9) with negative controls; the probe cannot pass vacuously (no target present is `missing`).

**Residuals outside Writ's claim (recorded, not mitigated by Writ):** an agent can serve look-alike pages on other loopback ports; exact Origin and RP validation (D-041) refuses assertions made for them, but the human must use the configured approval origin. Agent output shown in the human's terminal is untrusted (escape sequences; OSC 52 clipboard writes should be disabled in the terminal emulator). The human must never execute content from an agent-writable directory as the human uid (git hooks, build files and editor tasks in a shared working copy would run with the human's authority); the governed profile provides no directory writable by both, and agent output reaches the human's files only through governed `fs.write` (J-7).

**Shared-user installations: ADVISORY ONLY (D-046).** If an agent uid equals a desktop uid, no desktop uid is configured, or P-AGENT-DESKTOP is not `passed`, the readiness report labels the installation `advisory-shared-user`: governed jobs and governed writes refuse (M5-D2), the approval page shows a fixed banner that approvals on this installation are not protected against the agent, and no report or evidence claims agent-proof approval. Approval from a separate device (J-10 C-1 option (c)) is a later option, not a governed configuration in M5.

## J-2 Local RPC over Unix sockets (review M-6, L-1, L-4, L-5)

- **Sockets:** `SOCK_STREAM` sockets created by systemd socket units (`SocketUser=writ`, `SocketGroup=writ-agents`, `SocketMode=0660` for `host.sock`; `SocketGroup=writ`, `SocketMode=0600` for `admin.sock`) and passed to `writ-serviced` (J-8). The service runs with umask 0077 and never creates agent-reachable files itself.
- **Admission before any read:** on accept the service reads the peer credentials (`SO_PEERCRED`, Tokio `UnixStream::peer_cred` or `writ-hostsys`) and decides admission **before reading a single byte**. Refused: an unlisted uid; uid or gid 65534 (the overflow id seen for peers in another user namespace with unmapped ids); uid 0 on `host.sock`. The pid is recorded for audit only, never used for authorization.
- **Connection caps:** a global cap on open connections, a per-uid cap, per-connection idle and per-request deadlines; at the cap, new connections are accepted and closed at once (no read).
- **Frames:** 4-byte big-endian length, 1-byte frame type (`0x01` control, `0x02` ingest data), payload. The length is checked against the maximum for that frame type on that endpoint **before any allocation** (control 64 KiB, data 1 MiB); payloads are read into bounded buffers. A control payload is one UTF-8 strict JSON document parsed by the kernel parser (INV-41). Any violation closes the connection with a generic error (INV-18). One request in flight per connection. No ancillary data (`SCM_RIGHTS`, `SCM_CREDENTIALS`) is accepted; a message carrying it closes the connection.
- **Scope binding:** configuration maps each (socket, uid) to exactly **one** (tenant, project) binding; no request field selects or changes scope. A uid needing two projects gets two configured sockets (or is refused).
- **Authority follows the descriptor:** admission binds the connection to the uid that connected; whoever holds that connected descriptor acts with that uid's authority for the connection's lifetime. This is documented for clients: never pass a connected descriptor to a less trusted process.
- **Idempotency scoped by OS principal:** the broker idempotency key used for a request is derived from (`os_principal`, client key) inside the service, and `status.receipt` answers only for receipts of the same `os_principal`, tenant and project; two uids can neither collide nor probe each other's keys.
- **Clients verify the server:** the hook client, CLI client and MCP shim read `SO_PEERCRED` of their connection and refuse to send anything unless the peer uid is the configured `writ` uid.
- **What admission proves:** the OS principal of the connecting process only (M5-D7), recorded as `os_principal: "uid:<n>"`, `verified_by: "so_peercred"`.
- **Endpoints:** `host.sock`: `host.event`, `effect.request` (M5b), `snapshot.ingest.*` (J-4), `status.receipt`. `admin.sock`: `readiness`, `registry.*`, `keys.reload`, `keys.revoke` (J-10 Q-3), never dispositions that unblock or abandon.
- **Not MCP.** A Writ-internal protocol; MCP exists only in the agent-side shim.

## J-3 Key source (review M-3, L-2)

```text
broker::keys
  enum KeyPurpose { Ingress, Permit, AcceptanceRecord, RunnerAttestation }
  struct KeyId(String)                         // "<purpose>/<label>", [a-z0-9._-], at most 64 bytes
  struct KeyValidity { not_before, not_after }   // trusted time, whole seconds
  trait KeySource {
      fn key(&self, purpose: KeyPurpose, id: &KeyId, now: Timestamp) -> Result<KeyStatus<'_, Material>, KeysUnavailable>;
      fn issuing_key(&self, purpose: KeyPurpose, now: Timestamp, lifetime: Duration) -> Result<(KeyId, &Material), KeysUnavailable>;
  }
```

The purpose-typed rings (`KeyRing`, `AcceptanceKeyRing`, `RunnerKeyRing`) are implemented on top of a `KeySource`; `KeyStatus` gains `Expired` and `NotYetValid` (refuse like `Revoked`). Implementation `writ-keys::FileKeySource`:

- **File format** `writ-key/1`: strict JSON `{"contract":"writ-key/1","purpose","key_id","not_before","not_after","material"}`, `material` hex of at least 32 bytes. One key per file; **the file name must equal the encoded `key_id`** (`/` replaced by `_`, suffix `.json`), otherwise refused.
- **Loading:** open `/var/lib/writ/keys` with `openat2` (`RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS`): directory owned by `writ`, mode 0700, no access or default ACL, every ancestor owned by root or `writ` and not group- or other-writable. Each file: `openat2` relative to that descriptor with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV` and `O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`; `fstat`: regular file, owner `writ`, mode exactly 0600 or 0400, no ACL, `nlink == 1`, size at most 4 KiB; the read is bounded (at most the maximum plus one byte; more is refused). Failures refuse that key with an operator diagnostic (never the material).
- **Key registry and ids (ledger):** `key_registry` records every key id ever loaded with its purpose and the digest of its material (SHA-256 under a domain-separation prefix). An id presented again with different material, a material digest already registered under another id or purpose, and an id or material digest that was ever revoked are refused at load. **Ids are never reused.**
- **Revocation:** `key_revocations` (key id, material digest, purpose, revoked_at, actor, reason) in the ledger; **revoked material is refused under any id**. The revocation lookup runs **inside the ledger transaction that consumes the authenticated object**: for seals, inside T-reserve and again inside T-dispatch; for permits, inside the ledger transaction opened by the verification callback within the adapter transaction; for acceptance records and runner attestations, inside the promotion transaction. No cache. Revocation is recorded through `admin.sock` (`keys.revoke`, J-10 Q-3).
- **Issuing:** revoked, expired and not-yet-valid keys are never selected. `issuing_key` selects the valid key with the latest `not_before` whose `not_after` is at least `now + lifetime + margin` (lifetime of the object it authenticates; margin configured, default 60 s); if none qualifies, issuing refuses (fail closed) rather than producing an object that would outlive its key.
- **Key ids inside the MAC (versioned contracts):** permits gain `key_id` (new permit contract version) and seals gain `key_id` (new seal version, `{"adapter_id","key_id","mac"}`); in both, `key_id` is part of the MACed canonical bytes. Older versions are refused once the service runs with the file key source.
- **Rotation:** provision a new key with a later `not_before` and an overlap at least the longest lifetime of what the old key authenticated (permits 30 s; seals per request; records and attestations their freshness window); the old key becomes verify-only and then expires or is revoked.
- **Memory:** material is held in buffers zeroized on drop (`zeroize` after review, J-0); never in `Debug`, logs, readiness reports, evidence, command lines or environments; a canary scan in tests covers logs, reports and the repository.
- **Provisioning:** operator procedure on the reference host, as `writ`: material from the OS random source, temporary file in the key directory, `fsync`, rename, `fsync` of the directory; `keys.reload` loads it.
- **Failure:** unknown, revoked, expired, not-yet-valid, unreadable or integrity-failing keys refuse with the existing codes; an unreadable directory is `KeysUnavailable`.

## J-4 Snapshot store

`writ-snapshots-1`, a separate SQLite file owned by `writ-serviced`, using the ledger's identity and ownership pattern (canonical path, one hard link, `.owner` lock under the lifecycle gate, bound at creation to one `LedgerId`) and **owner-epoch fencing** like the ledger (the epoch is incremented at open and checked at the start of every write transaction; review M-2). WAL with `synchronous=FULL`.

- **Model.** `(tenant_id, project_id, snapshot_id)` with the `writ-snapshot-manifest/1` digest over `[{path, digest}]` sorted by path. `snapshot_id = "snap-" + hex(D-006 digest of {"contract":"writ-snapshot-id/1", tenant_id, project_id, manifest_digest})`. Tables `snapshots`, `snapshot_files`, `blobs` (by file digest). No `UPDATE` or `DELETE` in the API; triggers refuse updates.
- **Ingest (M5-D17).** `snapshot.ingest.begin` (scope from the connection binding), `snapshot.ingest.file {path, size}` plus data frames (digest computed as bytes arrive, sizes enforced), `snapshot.ingest.commit {claimed_manifest_digest optional}`: one transaction validates the manifest (valid paths per `valid_snapshot_path`, bounded length and depth, valid UTF-8, no control characters, no duplicates, no path that is a proper prefix directory of another, no two paths equal after Unicode normalization), computes the manifest digest, checks a claimed digest (mismatch refuses; never authority), inserts and commits. A crash before commit leaves nothing visible; temporary data is removed at open. No agent pathname is ever opened.
- **Bounds** per file, per snapshot, per session and per scope; exceeding one refuses `SNAPSHOT_LIMIT`.
- **Reads** re-verify every blob digest and the manifest digest on every consumption; mismatch fails closed.
- **Trust.** `immutable()` is true only for a store opened with a `VerifiedDeployment` (J-9); never a caller flag.
- **Retention.** No deletion in M5 (quotas bound growth); deletion with reference checks is deferred to CO-M4X-03 (M9).
- **Binding.** The broker's `Trust::snapshots` and the runner's `SnapshotContent` are the same instance.

## J-5 Containment (revision 5: BINDING; D-046 H-2)

- **Readiness** comes only from the probes (J-9) run at start and rechecked periodically and before each job: the launcher socket reachable and its `hello` facts equal to the pinned values (J-11.2); digests of `writ-cgroup-exec`, `writ-job-launcher`, the launcher unit files and the launcher configuration (hashed by `writ`, which can read them) unchanged; the private bubblewrap digest and runtime profile digests as reported by the launcher equal to the pinned values (`writ` cannot read the 0750 copy); `writ-jobs.slice` not populated between jobs. No version comparison. A failing check sets the guarantee `false`; `RunnerRequirements::production()` refuses; no uncontained fallback.
- **Job identity (D-046 H-2):** every job process runs as `writ-job` with no supplementary groups, never as `writ`, and never inherits `writ`'s groups, keys, descriptors or state access. Identity, resource limits, cgroup placement, `no_new_privs` and the privilege drop are established and verified by the root launcher before any job instruction executes (J-11.4).
- **Cgroup.** Job cgroups live in the launcher instance's root-owned delegated subtree `writ-jobs.slice/writ-job-launcher@<instance>.service/job`, with `memory.max`, `memory.swap.max = 0`, `memory.oom.group = 1`, `pids.max`, `cpu.max` written before any job process exists, within root-configured maxima and the unit's own ceilings (J-11.3). `writ.service` has no delegation and cannot write any cgroup file.

Never bound: `/var/lib/writ` (including `run/`), `/var/lib/writ-jobs` other than the job's own `work/`, `/run/writ`, `/run/writ-launcher`, `/etc/writ`, `/etc/writ-launcher`, `/srv/writ`, `/home`, `/run/user`, `/sys/fs/cgroup`, the host `/proc`, any socket. `--die-with-parent` is convenience only. Landlock optional defence in depth.

A change refuses until re-registration.
- **Termination** is owned by the launcher: `cgroup.kill`, then wait for `populated 0` (bounded); if it does not empty, the job is failed, the instance is left for systemd to stop, and readiness drops (J-11.5). Process-group signals are secondary only. `writ` stops a job only by `cancel` or by closing its connection.

Operator abandonment of a `started` run: J-11.9 (`run_abandon`).
- **Concurrency:** one job at a time on the host (J-11.7).

## J-7 `fs.write` adapter recovery contract (revision 3)

Revision 3 applies the re-review of revision 2 (N1..N3, L-a..L-h); verdict: ready to implement. Review ids F*, L1..L4 refer to revision 1, N* and L-a..L-h to the re-review.

### J-7.1 Scope, layout and canonical targets

- Action kind `fs.write`; resource `file:<tenant>/<project>/<root id>/<relative path>`; attributes bound by the action digest: `snapshot_id`, `manifest_digest`, `source_path`, `content_digest`, `mode` (`create_only` or `replace_if`), `expected_prior_digest` (`replace_if` only).
- **Root layout (F3):** each configured root `R` (under `/srv/writ/targets/`) contains exactly `R/staging` (0700) and `R/tree` (the published tree). Targets are resolved **only beneath `tree_fd`**; staged and displaced files live only in `staging`. Both are on the same filesystem and mount as `R` (checked at open).
- **Canonical relative paths (F3, F11):** valid UTF-8; components separated by single `/`; no leading or trailing `/`, no empty, `.` or `..` component, no NUL or control character; at most a configured length and depth. The **target key** is this exact byte string; no normalization is applied and none is needed because case-folding directories are refused (F11).
- M5 writes regular files into **existing** directories only; a missing parent, a directory, non-regular file or `nlink > 1` at the target is a precondition failure (J-7.5).
- **Overlap (F11):** configured roots must not be equal to, inside, or contain another root (checked at open by walking parents from each root descriptor with `..` and comparing identities); overlapping configuration refuses to open.

### J-7.2 Filesystem identity, descriptors and the mount rule (F2, F10, F11, L-c, L-g)

- **Persisted identities** are `{fs_uuid, ino, btime}` plus, when it can be read without `unsafe` code, the inode generation (`{fs_uuid, ino, btime, generation}`); `last_identity` and every recorded target identity also carry the content `digest` (L-d). `fs_uuid` is the filesystem UUID (`FS_IOC_GETFSUUID` only through a safe wrapper; otherwise the superblock UUID recorded by the operator at root creation and verified at every open by resolving the root's `st_dev` to its block device and the udev `by-uuid` link; **any failure of that resolution refuses to open**, L-c). `st_dev` and `mnt_id` are **never persisted**.
- **`STATX_BTIME` in every result (L-c):** every `statx` call requests `STATX_BTIME` (and `STATX_MNT_ID` where the mount rule applies); a result whose mask lacks `STATX_BTIME` is an observation failure (R9 in recovery, `TxFailure` in apply), never an identity without birth time.
- **Journal binding:** the journal records `fs_uuid`, the root's `{ino, btime}` (and generation if read), the ledger id and the root id; an open with any difference refuses.
- **Mount rule, re-derived at each open:** at open the adapter records the root's `mnt_id` and `st_dev` for **this adapter lifetime only**. Every per-operation resolution uses `openat2` with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV`, and every directory and file reached must report the same `mnt_id` and the same `st_dev` as at open (L-c); the persisted `fs_uuid` is checked at open. Mount crossings are thereby refused explicitly (M5-D8).
- **Clones and rollback (L-c):** a filesystem clone or a VM snapshot rollback can reproduce an identity that the journal has seen; such a state is caught by R11 (target differs from `last_identity`, including digest) and by the final row R-other of the decision table; it is never treated as evidence of completion beyond what those rows allow.
- **Descriptors (L-g):** every descriptor the adapter opens (journal files, root, `tree`, `staging`, parent directories, staged and target files, the `flock` descriptor, the `/run/writ/state` mark files) is opened with `O_CLOEXEC`.
- **Ownership and ACLs (F10):** at open and per operation, every directory on the path (`R`, `staging`, `tree`, each parent) is owned by `writ`, not group- or other-writable, and has **no access or default ACL** (`system.posix_acl_access`, `system.posix_acl_default` absent); staged and target files have no access ACL.
- **Locks (F11):** the journal's `.owner` lock, plus an exclusive `flock` on the descriptor of `R/staging` held for the adapter lifetime (refuses a second journal or adapter for the same root even through another path).
- **Filesystem allow-list:** ext4 with `has_journal` or xfs, without the `casefold` feature (operator-recorded and probed, J-9 P-FS-TYPE); network, FUSE, overlay and tmpfs refuse.

### J-7.4 Journal, operation identity and the unrecoverable mark

`writ-fseffects-1`, owned SQLite file per root, WAL with **`synchronous=FULL`** (F6), owner-epoch fencing (M-2), bound to one ledger and one root identity.

- `ops`: `op_id` (`fsop-<permit id>`), `permit_id` (unique), tenant, idempotency key, request fingerprint, root id, `target` (canonical key), mode, `expected_prior` (`{fs_uuid, ino, btime, generation?, digest}` or `absent`), `content_digest`, `snapshot_id`, `staging_name` (`<ledger id short>-<op_id>`, F11), `state` (`intent`, `abandoned`, `staged`, `resolved`), `staged_identity` (`{fs_uuid, ino, btime, generation?, size, digest}`; set at `abandoned` or `staged`), timestamps.
- `outcomes`: `op_id`, `operation_evidence` (`completed`, `not_completed`, `unknown`), `desired_state` (`verified`, `differs`, `absent`, `unknown`; L1), `result` (`applied`, `failed`, `unknown`), `reason`, `target_identity_after`, `displaced_identity` (`replace_if`), recorded_at, boot id.
- `targets`: `target`, `blocked_by`, `tainted` and reason, `last_identity` (with digest).
- `root_state`: `unrecoverable_boot_id` and reason (N3, F12).
- Partial unique index: at most one op with `state` not `resolved` per target.

**`resolved` is terminal (N2).** An op with a recorded outcome (`applied`, `failed` or `unknown`) is never revisited by recovery; `unknown` stays `unknown` forever. Only an `fs_target_release` disposition (J-11.9, D-046 Q-3) can unblock or untaint a target, and it never changes a recorded result.

**Operation-specific evidence.** The staged file is created by this operation (exclusive create under its unique staging name) and its identity is durably recorded before the rename. Neither staged nor displaced files are unlinked before the op's resolution is committed (F5), except a file the live apply itself created and whose identity it has just recorded (L-b, J-7.5). Content equality is never evidence (M5-D8).

**`desired_state` (L1)** is computed for every recorded outcome: `verified` when the target's identity equals the staged identity and its re-read digest equals `content_digest`; `differs` when the target exists with another identity or digest; `absent` when there is no target; `unknown` when the target cannot be observed.

**Unrecoverable root (N3, F12).** Any SQLite I/O error (`SQLITE_IOERR` family, `SQLITE_FULL`, `SQLITE_CORRUPT`) on the journal, and any `fsync` error on the journal's filesystem or on the root's filesystem, **disables the adapter for that root until reboot**. The mark is recorded **first** as a file `/run/writ/state/fs-unrecoverable-<root id>` (directory `/run/writ/state`, `writ:writ` 0700; `/run` is a tmpfs, so the mark is boot-scoped) containing the current boot id (`/proc/sys/kernel/random/boot_id`) and the reason, written and `fsync`ed, **then** in `root_state` if the journal still accepts a write. If the file mark cannot be recorded, the adapter refuses every operation on that root and refuses to open it again in this boot. At open, a mark file for the root or a `root_state.unrecoverable_boot_id` equal to the current boot id refuses to open (recovery draws no conclusions in this boot). After a reboot the old `root_state` mark is kept as history and recovery runs normally. Reason: after a write-back or `fsync` error, Linux may drop dirty pages and report later `fsync` calls as successful, so same-boot observations are not trusted.

### J-7.5 Normal path, results and crash boundaries

**Concurrency (F1, L-a).** One **adapter-wide exclusive lock** (in process) is held by `apply` from T-intent to its return and by recovery for its whole run. Recovery runs at journal open before any operation is accepted and before broker reconciliation reads evidence; an operator-requested recovery in the service takes the same lock. **Re-observation inside `apply`** (F8) calls the recovery routine with the guard that `apply` already holds (the routine takes the guard by reference and never acquires the lock itself), so there is no re-entrant deadlock. **Out-of-process recovery** (an operator tool) must hold the journal's `.owner` lock, so it can run only while no service owns the journal. Recovery skips any op whose `op_id` is in the in-memory set of live applies (defence in depth).

**Results (F9, L-e; documentation amendments of `EffectAdapter::apply` and `TxFailure`).**

- `Ok(Ok(Applied))` only after T-outcome `applied` is committed.
- `Ok(Ok(Failed))` only after a committed `failed` outcome with a recorded `reason`, for: `TARGET_UNRESOLVED` (another op on the target is unresolved), `TARGET_TAINTED`, `TARGET_PRECONDITION_FAILED` (for `create_only` the target exists; for `replace_if` no regular single-link file or a prior digest different from `expected_prior_digest`; missing parent; directory or non-regular target), each committed in T-intent with `operation_evidence = not_completed`; `EEXIST` from `RENAME_NOREPLACE` (F8); and `STAGE_FAILED` (a staging failure resolved inline, L-b). These are **consumed `Failed` results, not refusals**: the permit was valid and is consumed, the receipt becomes `observed_failure`, and `EffectEvidence` gains the `reason`.
- **`Err(TxFailure { stage: TxStage::Effect, outcome_unknown: true, .. })` for every other failure after T-intent** (filesystem errors, verification failures, re-observation without a definitive row). New stage value `TxStage::Effect` (`"effect"`): a failure after durable intent, in the non-transactional effect; `outcome_unknown` is always `true` for it. Commit failures of the journal's own transactions keep `TxStage::Commit` (`outcome_unknown` true for an issued commit). The `TxFailure` documentation is amended accordingly (today it describes SQL stages only). The receipt stays `dispatched`.
- **Unrecoverable root:** the outer `Err(TxFailure { stage: TxStage::Begin, error: Unavailable { code: "ROOT_UNRECOVERABLE" }, outcome_unknown: false })` before any permit check (externally `LEDGER_UNAVAILABLE`, D-025 B); nothing is consumed.

Before T-intent commits, failures follow the existing contract (`LEDGER_UNAVAILABLE` before permit checks; refusals roll back).

### J-7.6 Recovery and reconciliation decision table

Recovery holds the adapter-wide lock or `apply`'s guard (L-a). If the root is marked unrecoverable for the current boot (N3), it does not open the root and draws no conclusion. Otherwise, before reading, it reopens the journal connection if any journal commit failed since open (F6); it makes the observed state durable (`fsync` of `tree` parents, `staging` and the target if present; any error marks the root and stops); then observes **T** (target: `absent`, `= staged`, `= prior`, `other`) and **S** (staging name: `absent`, `= staged`, `= prior`, `other`) by identity, with `nlink`, and the digest where a row needs it. Only ops whose `state` is `intent`, `abandoned` or `staged` are processed; `resolved` ops, including `unknown` ones, are never revisited (N2).

**Row order (N1):** rows are tried top to bottom; the first match decides. For `staged` ops the unsafe rows (R9, R8, R4, R3y, R6) are tried before the completing rows (R3, R3x, R5), and R-other catches everything not matched.

Release requires the worker-gone evidence of J-11.9, for which `ops` gains `owner_epoch` recorded at T-intent; recorded results never change.

**R1, R1c and R5 soundness.** They depend on E1, E2 and E4 and on the protocol order (no rename before a durable T-staged; staged and displaced files kept until resolution, except the live apply's own abandoned file whose identity is recorded first). **Power loss (L4):** after a power loss, R5 means "not durably applied": the rename may have executed and its content may have been transiently visible to readers of `tree`, but it did not survive; consumers rely on the journal outcome, never on content they observed.

**Repeated identical content and later writes (L-d).** Distinct ops have distinct staged identities, so identical bytes never produce shared evidence; `replace_if` to the same bytes is evidenced by identity like any other. A later op compares the target with `last_identity` (identity and digest, R11): an external change is detected whenever the identity or the digest differs. An in-place rewrite that keeps the same inode and writes identical bytes is not distinguishable, and it changes nothing a consumer can observe.

### J-7.7 Evidence routing and partial availability (L3, L-f)

- The broker routes `apply`, `inspect` and `evidence` by action kind and, for `fs.write`, by the root id in the bound request's resource, to that root's journal. The by-permit-id evidence query used in reconciliation asks **every** adapter (controlled store, runner, every per-root `fs.write` journal); a record in more than one is an integrity failure.
- `evidence` and `inspect` return evidence only for resolved ops with result `applied` or `failed`; for an unresolved or `unknown` op they return none, so the broker answers `RECONCILIATION_REQUIRED` and the receipt stays uncertain.
- **One unreadable root (lead decision recorded here):** an op is recorded only in the journal of the root named by its bound request (T-intent checks that the request's root id equals the journal's), so a receipt whose bound request is not an `fs.write` for that root **can be ruled out** of that journal. Reconciliation of such receipts proceeds with the other adapters, and the skipped duplicate check against the unreadable journal is recorded in the reconciliation audit. Only receipts whose op cannot be ruled out (an `fs.write` naming the unreadable root, or a receipt whose bound request cannot be read) are refused (`LEDGER_UNAVAILABLE`) until the root is readable.

## J-8 Graceful shutdown (review H-1, M-2)

**Sockets held across restarts.** Option (a), preferred: systemd socket activation (`writ-host.socket`, `writ-admin.socket`, `writ-approval.socket` for the loopback TCP port) holds the Unix sockets and the TCP port across service restarts, so no other process can bind them in between. Option (b): bind the approval port below `net.ipv4.ip_unprivileged_port_start` with `CAP_NET_BIND_SERVICE`, with a probe that the agent uid cannot bind it. In either case `writ-serviced` **refuses to start** if it does not receive or cannot bind every configured socket, and verifies the received sockets' type, address and mode.

Sequence (CO-M4X-05; M5-D16):

1. **SIGTERM or SIGINT:** enter `stopping`. Listening sockets **stay open**; new connections and new requests on open connections are answered with the generic refusal `SERVICE_STOPPING` (the loopback page answers 503). No new effect, job, ingest or ceremony begins.
2. **Drain** (configured, default 10 s, maximum 30 s): requests in progress finish. Ceremonies not finished are left (challenges stay issued and expire). Uncommitted ingest sessions are abandoned (nothing visible).
3. **Effects:** an `fs.write` in progress runs to its return within the drain period; whatever its state, recovery handles it (J-7.6).
4. **Runner jobs:** after the drain period, `cgroup.kill` and verified empty (J-5); the run is finished `failed` with `terminated_shutdown` if T-finish succeeds, otherwise stays `started`.
5. **Release ownership:** join every task holding a store handle, then drop the broker, the effect store, fs journals and snapshot store, then the ledger (each `OwnerLock` unlocked before close under the lifecycle gate); exit 0. Owner-epoch fencing on the snapshot store and fs journals (J-4, J-7.4) guarantees that a straggler holding an old handle cannot write after a new owner opens.
6. **Second signal or hard deadline** (drain plus 5 s): exit immediately non-zero; the OS releases locks; uncertain outcomes are preserved. `KillMode=mixed`, `TimeoutStopSec` above the hard deadline (systemd then kills the whole unit cgroup, including job cgroups).

Tests: SIGTERM during a ceremony, an ingest, each `fs.write` boundary and a running job; refusals answered while stopping; another process cannot bind the sockets during a restart; a new owner opens immediately after exit; second signal; hard deadline; no result changes because of shutdown except step 4.

### J-11.1 Scope and trust

The launcher is a new **root** component in the trusted computing base. It does exactly one thing: on a typed request from `writ`, establish one job as `writ-job` inside a root-owned cgroup and the pinned bubblewrap profile, relay its output, and terminate and verify it. It accepts **no** arbitrary privileged command, uid, gid, group, mount, bind, unit property, capability, environment for a privileged step, or shell evaluation, and it never executes anything with privilege other than the fixed `writ-cgroup-exec` and the private bubblewrap (which runs as `writ-job`). It is written in safe Rust (`unsafe_code` forbidden), built with `panic = "abort"`, single-threaded and synchronous (no Tokio; a `poll` loop, M3), in crate `writ-containment` (new bin `writ-job-launcher` beside `writ-cgroup-exec`), depending only on `writ-hostsys` and the kernel's strict JSON parser; no new dependency.

The launcher treats **`writ` as less trusted than root**: a compromised `writ` must not gain through it anything beyond running code as `writ-job` within the maxima, on input it could already read.

- **Not set, with reasons:** `ProtectControlGroups` (systemd 255 has no private mode; it would make the delegated subtree read-only), `RestrictNamespaces` (bubblewrap needs user, mount, pid, net, ipc, uts and cgroup namespaces), `MemoryDenyWriteExecute` and `RestrictAddressFamilies` (inherited by jobs; they belong to the runtime profile), `ProtectProc=invisible` (L10: it would hide the `/proc` entries of `writ-job` processes that the residue and verification checks must see; the residual, that the launcher view shows other processes' `/proc` metadata to an escaped job, is recorded).
- **Drop-in and default detection (L2):** readiness refuses if any drop-in can apply to the units: directories `writ-job-launcher@.service.d`, `writ-job-launcher@<instance>.service.d`, the dash-prefix forms `writ-job-launcher-.service.d` and `writ-job-.service.d`, the top-level `service.d`, `socket.d` and `slice.d`, under `/etc/systemd/system`, `/run/systemd/system`, `/usr/lib/systemd/system` and `/usr/local/lib/systemd/system`; `systemctl show -p DropInPaths` of the socket, template, a running instance and the slice must be empty; `/etc/systemd/system.conf` and `system.conf.d` defaults that alter limits, accounting or capabilities are recorded and digested.
- **`writ-jobs.slice`:** aggregate `MemoryMax=`, `TasksMax=`, `CPUQuota=`; it contains only launcher instances. **Memory budget (L5):** the launcher's own bound plus the largest permitted `memory_max_bytes` is at most the unit's `MemoryMax`; configuration violating this refuses to load.
- **Admission before any read:** the instance takes the connection from systemd (`LISTEN_FDS=1`, `LISTEN_PID` equal to its pid), immediately moves it to a high descriptor with `F_DUPFD_CLOEXEC` and closes descriptor 3 (M1), reads `SO_PEERCRED` and refuses unless the peer uid equals the configured `writ` uid (uid 0, the overflow uid 65534, agent, job and desktop uids are refused), **before reading a byte**. Ancillary data closes the connection. Framing is J-2's; **from `writ` only control frames (`0x01`) are accepted; a data frame (`0x02`) closes the connection** (L7).
- **Handshake:** the launcher sends `hello` first: `{"contract":"writ-launch-hello/1","launcher_digest","exec_digest","bwrap_digest","bwrap_profile_digest","apparmor_profile_digest","runtime_profiles":[{id,digest}],"maxima_digest","instance"}`. `writ` sends its request **only after** a `hello` whose facts equal its pinned values; otherwise it closes. EOF before `hello` (including a refusal by `MaxConnections`) means the request was never sent. The request must arrive within a launcher-configured deadline after `hello` (M3), otherwise the instance closes with nothing started.
- **Readiness rechecks (L4):** a periodic recheck that finds the socket busy (`MaxConnections` refusal) does **not** withdraw readiness; the current connection's `hello` is the evidence for that period. Only a `hello` that differs, a failed socket unit or a failed static check withdraws it.

### J-11.3 Request `writ-launch/1` and validation

One control frame, strict JSON (INV-41), unknown fields refused:

```text
{"contract":"writ-launch/1",
 "job_id":        "<run id>",                       // [a-z0-9-], at most 64 bytes; echoed in every frame
 "runtime_profile":"<id>",                          // must be in the /etc/writ-launcher allow-list
 "program":       "<canonical relative path>",      // J-7.1 path rules; executed as /work/<program> inside the sandbox
 "args": [...], "env": [[name, value], ...],        // bounded counts and lengths; names [A-Za-z_][A-Za-z0-9_]*, unique
 "limits": {"wall_time_ms","memory_max_bytes","pids_max","cpu_max_quota_us","cpu_max_period_us",
            "output_max_bytes","input_max_bytes","file_size_max_bytes","nofile_max","sigpending_max"}}
```

- **The source is derived, not named (M4):** the source directory is always `run-<job_id>` under `/var/lib/writ/run`; there is no path or path-id field.
- Every limit is required and must be at most the root-configured maximum (`/etc/writ-launcher`), itself within the unit's ceilings and the memory budget (L5); a value above refuses (`LAUNCH_LIMIT_EXCEEDED`); nothing defaults upward.
- `args` and `env` reach only the unprivileged job: they are placed after bubblewrap's `--` and in `--setenv` options; they never form part of a privileged step, an option to bubblewrap, a path the launcher opens, or a shell string. The bubblewrap argument vector is built by the launcher from the fixed profile and the allow-listed runtime profile; no request field adds a bind, namespace, capability or option.
- **Source copy (M4, M5):** `/var/lib/writ/run` is `writ:writ` 0750 and `/var/lib/writ` 0710 (J-1); the launcher reads by **group** membership, never by DAC override. It opens `/var/lib/writ/run` by descriptor, then `run-<job_id>` with `openat2` (`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV`), and walks it **iteratively** (explicit stack, no recursion) by descriptor. For each entry: `statx` with `AT_SYMLINK_NOFOLLOW` first, refusing anything that is not a directory or regular file; then `openat2` with the same resolve flags and `O_NONBLOCK | O_NOFOLLOW | O_NOCTTY | O_CLOEXEC` (plus `O_DIRECTORY` for directories); then `fstat` and require the same `st_dev` and `st_ino` as the `statx` (a swap between the two refuses). Every entry owned by `writ`, not group- or other-writable, no ACL, regular files with `nlink == 1`. Depth, entry count and total bytes are bounded, the byte bound applied to **bytes actually read**, never to `st_size`. The copy goes to `/var/lib/writ-jobs/job-<instance>/work/` (created by root) and every copied entry is then `chown`ed to `writ-job` (directories 0700, files 0600, the program 0700). Any violation refuses before the helper is spawned. A compromised `writ` can thereby hand the job only bytes it already owns.
- **Capability drop after the copy (M5):** once the copy and `chown` are complete, the launcher drops `CAP_CHOWN` from its permitted, effective and bounding sets (rustix `thread` capset on the single thread), keeping only `CAP_SETUID` and `CAP_SETGID` for the helper's privilege drop.
- **Refusals** (`refused` frame, then close) are possible **only before the helper is spawned** (H1), so they are definitive: no job process existed. Codes: `LAUNCH_INVALID`, `LAUNCH_PROFILE_UNKNOWN`, `LAUNCH_SOURCE_INVALID`, `LAUNCH_LIMIT_EXCEEDED`, `LAUNCH_BUSY` (J-11.7), `LAUNCH_UNAVAILABLE` (a readiness or residue check failed). They are launcher diagnostics recorded by `writ`; the agent never sees them (generic external mapping, INV-44).

### J-11.4 Establishing the job (order; every step before untrusted execution)

**Gate invariant (H1).** The launcher holds the write end of the gate pipe (`O_CLOEXEC`). bubblewrap's `--block-fd` returns on **any** read result, including EOF, so closing the writer releases the job exactly like writing to it (**verify in VM** against the pinned bubblewrap 0.9.0 source: where the read happens, that EOF proceeds, and that the descriptor is closed before the program is executed). Therefore: **the gate writer is never closed, on any path, before `cgroup.kill` has been written and `populated 0` observed for `<unit>/job`.** Every error path after the helper is spawned calls the kill routine first and only then lets the writer close. With `panic = "abort"` there is no unwinding that could close it early; an abort or a crash of the launcher closes it by process exit, which is why a launcher crash after spawn is **uncertain** (J-11.6): the job may have been released unverified until systemd kills the instance cgroup. Its exposure is bounded by what the helper established before executing bubblewrap (uid, gid, empty groups, `no_new_privs`, rlimits, cgroup, the child AppArmor profile of H2). Optional hardening (not required): confining the helper and bubblewrap under the child profile until the gate opens.

1. **Readiness and residue** (J-11.7): own configuration and digests; the runtime profile's manifest digest recomputed; the residue checks.
2. **Prepare** the job directory and copy the source (J-11.3); drop `CAP_CHOWN`.
3. **Cgroup:** the launcher moves itself into `<unit>/supervisor`, enables `memory pids cpu` in `<unit>/cgroup.subtree_control`, creates `<unit>/job` and writes `memory.max`, `memory.swap.max = 0`, `memory.oom.group = 1`, `pids.max`, `cpu.max`. The unit path comes from `/proc/self/cgroup`, never from the request.
4. **Descriptor plumbing and spawn (M1).** Since step 0 every launcher descriptor is `O_CLOEXEC`/`FD_CLOEXEC` and the connection sits on a high descriptor. The launcher creates the gate pipe and the status pipe with `O_CLOEXEC`; immediately before spawning (single-threaded, so nothing else can fork in between) it `dup2`s the gate read end to descriptor 3 and the status pipe write end to descriptor 4 (`dup2` clears `FD_CLOEXEC` on the copies), spawns `writ-cgroup-exec` as root with a cleared environment and a launcher-built argument vector (0 is `/dev/null`, 1 and 2 are the output pipes), and closes 3, 4 and the originals of those ends in the launcher right after the spawn returns. **From this point no `refused` frame is ever sent**: every failure is `finished` with `start_failed` and kill evidence.
5. **Helper, before executing bubblewrap:** verifies it is single-threaded; lists `/proc/self/fd` and requires exactly `{0, 1, 2, 3, 4}` apart from the descriptor of the listing itself; opens `<unit>/job` by descriptor beneath its own unit cgroup; writes its pid to `cgroup.procs` and verifies `/proc/self/cgroup`; sets `RLIMIT_CORE = 0`, `RLIMIT_NOFILE`, `RLIMIT_FSIZE`, `RLIMIT_NPROC`, `RLIMIT_MSGQUEUE`, `RLIMIT_MEMLOCK`, `RLIMIT_SIGPENDING` (lowering only) and `oom_score_adj = 500`; sets `PR_SET_NO_NEW_PRIVS`; then `CommandExt::exec` of the private bubblewrap with `uid(writ-job)` and `gid(writ-job)` (the standard library calls `setgroups(0)`, `setgid`, `setuid` before `execve` when running as root; **verify** against the pinned toolchain's `std` source), with `--block-fd 3 --json-status-fd 4` and the fixed profile. Any helper failure exits non-zero before executing bubblewrap.
6. **Verify while the gate is closed (M2).** The launcher reads bubblewrap's JSON status from the status pipe (bounded, deadline) until it reports the sandbox child pid (**verify in VM** that bubblewrap 0.9.0 emits it before blocking on `--block-fd`). It then reads `<unit>/job/cgroup.procs` and, for **every** pid listed, `/proc/<pid>/status` as seen from the initial user namespace: `Uid` and `Gid` (real, effective, saved, filesystem) equal the kernel ids of `writ-job`, `Groups` empty, `NoNewPrivs: 1`; and requires that the listed set is exactly bubblewrap and its sandbox child. Capabilities inside the sandbox's own user namespace are not judged here (they are namespace-local); P-JOB-IDENTITY checks them after the gate. Any mismatch: kill (gate still closed), `finished` with `start_failed`.
7. **Release:** write one byte to the gate; send `started`.

### J-11.5 Descriptors, observation and termination

- **Job descriptors:** exactly 0 (`/dev/null`), 1 and 2 (pipes read by the launcher); the gate (3) and status (4) descriptors are closed by bubblewrap before the program runs (**verify in VM**; P-FD). `writ` holds **no** descriptor of any job process, pipe, cgroup or job directory, and no pidfd.
- **Event loop (M3):** one `poll` loop over the connection, the two output pipes and the status pipe, all non-blocking. Deadlines (request after `hello`, start, wall time, kill verification) come from the launcher's monotonic clock and configuration, never from `writ`'s behaviour. Output is forwarded as data frames tagged `stdout` or `stderr` through a **bounded outbound buffer**; if `writ` does not read and the buffer fills, or total output reaches `output_max_bytes`, the launcher kills with reason `output_exceeded`. Output is bytes, never interpreted.
- **Termination ownership:** only the launcher kills: at `wall_time_ms`, on `output_exceeded`, on a `cancel` frame, on EOF or error of `writ`'s connection, on SIGTERM, on any internal error. Kill = write `1` to `<unit>/job/cgroup.kill`, then wait (bounded, configured, default 5 s) for `populated 0` in `<unit>/job/cgroup.events`; reap the direct child.
- **Cleanup without DAC override (M5):** `work/` is owned by `writ-job`, so the launcher removes its contents by spawning the helper in **cleanup mode** in `<unit>/job` (as `writ-job`, `no_new_privs`, no bubblewrap): it removes `work/` beneath a descriptor (`unlinkat`, no symlink following, no mount crossing); the launcher then kills and verifies `populated 0` again, removes `<unit>/job`, and removes the now-empty root-owned `job-<instance>/` itself.
- **Result:** `finished` `{"contract":"writ-launch-result/1","job_id","request_digest","reason":"exited|signaled|timed_out|output_exceeded|cancelled|start_failed","exit_status","signal","kill":{"used","populated_zero"},"memory_events":{"max","oom","oom_kill"},"pids_events":{"max"},"cpu_usage_usec","output_bytes":{"stdout","stderr"},"digests":{"bwrap","bwrap_profile","apparmor_profile","runtime_profile","exec"}}`. `request_digest` is the D-006 digest of the request; `writ` refuses a result whose digests or `request_digest` differ (J-11.6) and maps the result to `JobOutput` or `JobFailure` (no attestation unless `exited` with `populated_zero`).
- **If the cgroup does not empty:** `finished` with `populated_zero: false`; the gate writer stays open, nothing is cleaned up, the launcher exits non-zero; systemd stops the instance (`KillMode=control-group`); `writ` fails the job, withdraws containment readiness and starts no job until `writ-jobs.slice` reports `populated 0` and the operator re-runs the probes.
- **How `writ` observes without control:** the frames above, plus read-only reads of `writ-jobs.slice/cgroup.events` (allowed under `ProtectControlGroups=yes`). Its only influence after the request is `cancel` or closing the connection, both of which only stop the job. J-8 step 4 is performed this way.

### J-11.5a AppArmor confinement of bubblewrap and its children (H2)

Following Ubuntu 24.04's `bwrap-userns-restrict` pattern, two profiles are loaded from `/etc/apparmor.d/writ-bwrap` (digest pinned):

- **`writ-bwrap`**, attached by path to `/usr/local/libexec/writ/bwrap` only: allows what bubblewrap itself needs (`userns`, `mount`, `umount`, `pivot_root`, capabilities inside its own namespaces, file access) and transitions **every program it executes** into the stacked child label with `px /** -> &writ-bwrap//&writ-job-child` (or the `pix` form used by the pinned Ubuntu profile).
- **`writ-job-child`**: `audit deny userns`, `audit deny capability`, otherwise permissive enough for the runtime profiles; executions inside it are `ix` (they stay in the child label), so no job descendant regains `userns` or capabilities, including by executing a copy of bubblewrap or the private copy itself.

`--disable-userns` in the bubblewrap profile stays as a second layer. **Verify in VM:** profile syntax and stacking semantics under the pinned AppArmor; attachment of `writ-bwrap` when executed under `no_new_privs` from the unconfined launcher; and that from the escape view (P-JOB-DENY) `unshare -U` and direct execution of the private bubblewrap yield no usable namespace.

### J-11.6 Failure modes

| Failure | Launcher | `writ` conclusion |
|---|---|---|
| socket missing, connect refused, socket unit failed, EOF before `hello`, `hello` facts differ | nothing started | job not run (request never sent); containment unavailable when the facts differ or the socket unit failed |
| no request within the deadline after `hello` | closes; nothing started | not applicable (`writ` did not send) |
| `refused` frame (only before the helper is spawned, H1) | nothing started | job not run; run `failed` with the diagnostic |
| failure after the helper is spawned (helper exit, status timeout, verification mismatch, gate write error) | kill with the gate closed, verify `populated 0`, then `finished` `start_failed` with kill evidence | job not run if `populated_zero` and the failure preceded the gate release; run `failed` |
| EOF or timeout after the request and before `refused` or `finished` | kills and cleans up anything it created when it sees EOF | **uncertain**: run stays `started`, never re-run; `writ` records `writ-jobs.slice` `populated 0` when observed (evidence for J-11.9) |
| launcher instance crashes, aborts or is killed after the helper was spawned | the gate closes by process exit and may release the job unverified; systemd kills the instance cgroup | **uncertain**, as above (H1) |
| launcher OOM-killed (L8) | the kernel kills the launcher (its `OOMScoreAdjust` makes the job the preferred victim, but not guaranteed); systemd then kills the instance cgroup | **uncertain**, as above |
| `finished` digests or `request_digest` differ from what `writ` sent and pinned (L8) | n/a | no attestation; run `failed`; containment readiness withdrawn until the operator re-pins or investigates |
| `writ` crashes or stops | connection EOF: kill, verify, clean up | at restart: wait for `populated 0`, runs stay `started` |
| `writ` stops reading output | bounded buffer fills: kill, `output_exceeded` | job outcome as reported |
| cgroup does not empty | gate stays open, no cleanup; instance stopped by systemd | job failed; readiness withdrawn (J-11.5) |
| job exceeds memory, pids, CPU, wall time, output, file size or signal queue | kernel limit or launcher kill | `finished` with the reason and counters; no attestation |
| job filesystem full | job sees `ENOSPC`; Writ state is on other filesystems | job outcome as reported |
| bubblewrap escape (H3) | the process remains `writ-job`, in `<unit>/job`, under the `writ-job-child` label and in the launcher unit's mount, IPC and network view; it is killed with the cgroup | it can reach only what P-JOB-DENY's escape view shows (by design, no Writ state, keys, sockets, homes or host network); anything it persists in `writ-job`-writable locations is **detected** by the residue checks before the next job (which then refuses), not prevented; no concurrent job exists to reach (J-11.7) |
| configuration, unit, drop-in or binary changed | refuses (`LAUNCH_UNAVAILABLE`) or `hello` differs | containment unavailable until re-pinned by the operator |
| kernel escape to root | out of scope; nothing holds | recorded limitation |

### J-11.7 Cross-job and cross-tenant isolation

**What a shared job uid does not isolate.** Between two processes running as `writ-job`, the kernel's uid checks allow: **signals** to any process they can name; **ptrace** and `/proc/<pid>/mem`, `environ`, `cwd`, `root` and `fd` links, limited only by Yama (`ptrace_scope >= 1` restricts to descendants) and by visibility; **`/proc`** metadata (`cmdline`, `stat`) of all of them; **files** owned by or writable by `writ-job`, including every job's `work/` and any world-writable location; **keyrings** keyed by uid (the user and user-session keyrings, depending on user-namespace keyring scoping); **IPC** (SysV objects, POSIX message queues, abstract Unix sockets) wherever the two share a namespace; and **per-uid kernel counters** (`RLIMIT_NPROC`, `RLIMIT_MSGQUEUE`, `RLIMIT_SIGPENDING`, inotify instances and watches, user-namespace counts, key quotas in `/proc/key-users`), which let one job deny service to another. Separate PID, IPC, network, mount and user namespaces per job hide these from each other **only while no job escapes its namespaces**; after an escape (the case H-2 exists for) all of the above apply to every concurrent job.

**Choice: serialize. One job at a time on the host.** Recommended over proving concurrent isolation because namespace isolation can be shown by probes only for the no-escape case, while D-046 requires that a shared uid not be relied on for isolation, and per-job transient uids are not available without a new owner decision. Enforcement, independent of `writ`'s scheduling: `MaxConnections=1`; per-instance `PrivateTmp`, `PrivateIPC`, `PrivateNetwork`, `KeyringMode=private` and the `TemporaryFileSystem` mounts for `/run`, `/dev/shm` and `/dev/mqueue` (J-11.2), so nothing a job leaves there survives its instance; `SystemCallFilter=~@keyring` so jobs cannot create or join keyrings at all; and the residue checks.

**Residue checks before every job (J-11.4 step 1; H3):**

- no process with any uid equal to `writ-job` on the host (scan of `/proc/*/status`);
- no other populated instance in `writ-jobs.slice`;
- `/var/lib/writ-jobs` contains no entry other than this instance's;
- `/proc/key-users` has no line for the `writ-job` kuid;
- no `writ-job`-owned inode in the **known writable locations** of the host view (`/tmp`, `/var/tmp`, `/dev/shm`, `/dev/mqueue`, `/run/user`, `/var/crash`, the jobs filesystem), checked per launch; the **full** search (`find -xdev -uid writ-job` over every writable host mount) is P-JOB-SERIAL's, run by the operator;
- any finding refuses `LAUNCH_UNAVAILABLE`, and each location has its own negative control in P-JOB-SERIAL.

**Core dumps (H3):** the reference image disables apport and sets a non-pipe `kernel.core_pattern` (a pipe pattern runs a root helper for `writ-job` crashes regardless of `RLIMIT_CORE`); `LimitCORE=0` and `RLIMIT_CORE = 0` hold; the setting is recorded in the readiness report and **verify in VM**.

Namespaces stay as defence in depth. Consequences: an escaped job can reach only itself and whatever it can persist in `writ-job`-writable places, which the residue checks find before the next job; throughput is one job at a time, consistent with the single-worker scope of M5a (CO-PROP-01 single worker). Concurrent jobs (M10 multi-worker) need per-job uids or a proved isolation argument, and therefore a new owner decision at that time.

### J-11.8 Key revocation over `admin.sock` (D-046 Q-3)

- **Request** `keys.revoke`: `{"scope":{"kind":"key_id","purpose","key_id"} | {"kind":"material","purpose","material_digest"},"reason"}`. **Explicit scope only:** one key id or one material digest of one purpose; no wildcard, no "all keys of a purpose", no un-revoke, no re-registration (J-3: ids and revoked material are never reused).
- **Validation (L9):** for `key_id`, the id must be registered in `key_registry` and the request's purpose must equal the registered purpose; the recorded material digest is the **registered** one, never a request value. For `material`, a digest registered under any id must have the requested purpose; an unregistered digest is accepted as a pre-emptive revocation of that purpose. Any mismatch refuses.
- **Authenticated OS peer:** `admin.sock` admits only uids in the configured `admin_uids` (default `[0]`: the operator procedure as root); agent, job and desktop uids are refused at configuration load if listed. Admission happens before any read (J-2). The peer proves an OS principal only (M5-D7), never a human.
- **Audit provenance:** the `key_revocations` row records key id, material digest, purpose, `revoked_at` (trusted time), reason (bounded, untrusted text, **escaped** wherever displayed or logged, L9) and actor `{"principal_kind":"os","os_principal":"uid:<n>","verified_by":"so_peercred","endpoint":"admin.sock","pid":<audit only>}`.
- **Ordering evidence:** the revocation runs in a `BEGIN IMMEDIATE` ledger transaction (L9) that also writes a `ledger_sequence` row (kind `key_revocation`, reference the revocation id), so it is serialized against, and ordered before or after, every reserve, dispatch, promotion and permit verification. A repeated identical revocation returns the existing row without a new one.
- **Effect:** only reduces authority. Unconsumed objects authenticated by the key are refused at use (J-3, in-transaction lookup); consumed uses, reservations and receipts are unchanged; nothing is refunded or redispatched.

### J-11.9 Unblock and abandon dispositions (D-046 Q-3)

**Two new versioned ceremony operations** on the approval page (`ChallengeOperation::FsTargetRelease`, stored `fs_target_release`; `ChallengeOperation::RunAbandon`, stored `run_abandon`), with `CeremonyOp` variants of the same names. They follow the M4 ceremony pattern (`revocation_binding`, `role_change_binding`): a fresh user-verified WebAuthn assertion by a human holding **`Operator`** in the target's tenant and project (S5 scope-containment rules; services never, O-8), over a single-use challenge of at most 120 s, consumed atomically with the disposition decision; identical-retry replay after an unknown commit; never through `admin.sock` (J-2).

**Binding** (`ChallengeBinding`): operation; verdict = the proposed disposition (`release` for `fs_target_release`, `abandon` for `run_abandon`); tenant and project; `target_id` = `fsroot:<root id>:<length-prefixed canonical target key>` or `run:<run id>`; `revision` = the journal's change counter (fs) or the ledger sequence high-water mark (run) at begin; `policy` = `NO_POLICY`; `context_fingerprint` over the `writ-disposition-context/1` context computed **by the service** from authoritative state, never from page input:

- **current state digest:** fs: D-006 digest of `writ-fs-target-state/1` (the `targets` row, every op on the target with state, identities and recorded outcome, the root's unrecoverable mark, and the T and S observations made under the adapter-wide lock at begin); run: digest of the run record, its permit, receipt state and recorded launcher evidence;
- the recorded results, displayed as **unchanged by this disposition**;
- the proposed disposition and its exact consequences (below);
- the **worker-gone evidence** (below).

At finish the service recomputes the context under the same locks; any difference refuses `DISPOSITION_STALE` and burns the challenge (D-042 S3).

**Precondition: the original worker cannot still act**, established at begin and again at finish, and recorded:

| Evidence | `fs_target_release` | `run_abandon` |
|---|---|---|
| owner epoch fenced | the op's `owner_epoch` (recorded at T-intent; this revision adds the column to `ops`) is lower than the journal's current epoch, or the op was written in the current epoch, is resolved and is not in the live-apply set | the run's `owner_epoch` (recorded at T-start; added to run records) is lower than the ledger's current epoch, or the run is not in the supervisor's live set |
| live-set discipline (M6) | the adapter-wide lock and the op's live-apply entry are acquired and released **by the thread executing `apply`**, never on its behalf, so an apply thread that is hung or still inside a filesystem call keeps both, and the disposition cannot proceed | the supervisor's live-set entry for the run is held by the thread that owns the launcher connection until that connection is closed and the result recorded |
| lock held | this adapter instance holds the journal `.owner` lock, the `flock` on `R/staging` and the adapter-wide lock for the whole finish | the supervisor holds its ownership and no launcher connection exists for the run |
| process gone | the previous owner's pid and start time (from its ownership record) no longer exist, or the recorded boot id differs from the current one; **and** `writ.service`'s `cgroup.procs` contains only the current main pid (M6: no straggler service process of any epoch holding descriptors) | same, for the `writ-serviced` that started the run |
| cgroup empty | not applicable | `writ-jobs.slice/cgroup.events` reports `populated 0` **and** no process with uid `writ-job` exists; or the run's boot id differs from the current one |
| unresolved work | every op on the target is `resolved` (an op in `intent` or `staged` refuses `DISPOSITION_PRECONDITION`: recovery has not concluded); the root is not marked unrecoverable for this boot (N3) | run state is `started` |

The evidence (values, observation times, boot id) is stored with the disposition. Missing evidence refuses `DISPOSITION_PRECONDITION`.

**What each disposition does, and nothing else:**

- `fs_target_release` clears `blocked_by` and `tainted` and sets `last_identity` to the identity and digest observed at begin (or `absent`). Staging files left by the target's ops (R1b's unrecorded file, R3y's or R6's kept files) are **not** touched; they are listed in the disposition and stay excluded from garbage collection. Later ops on the target are new operations with new requests, approvals, permits and idempotency keys, evaluated against the new baseline (R11).
- `run_abandon` sets the run to a new terminal state `abandoned` (versioned run-state value) with the disposition id. No attestation, output digest or result is recorded; the run's work directory may then be removed.

**Never:** a disposition never changes an `outcomes` row or a run's recorded result, never turns `unknown` into `applied` or `failed`, never changes a receipt or answers reconciliation (an `unknown` op still yields `RECONCILIATION_REQUIRED`), never refunds a use, reservation or key, never frees an idempotency key, permit id or key id for reuse, and never dispatches anything.

**Persistence and ordering (two databases; H4).**

1. **Ledger transaction:** consume the challenge, insert `dispositions` (`disposition_id` unique, operation, scope, `target_id`, state digest, proposed disposition, context fingerprint, worker-gone evidence, actor subject and credential, challenge id, `decided_at`, `status = decided`) and a `ledger_sequence` row (kind `disposition`).
2. **Journal transaction**, under the adapter-wide lock, **idempotent per `disposition_id`:** if `target_dispositions` already has a row for this `disposition_id`, do nothing; otherwise recheck that the state digest equals the decided one, apply, and insert `target_dispositions` (`disposition_id` **UNIQUE**, previous and new `blocked_by`, `tainted`, `last_identity`) in the same transaction.
3. **Ledger:** `status = applied`.

**Completion after a crash** (at the next adapter open, before any operation is accepted, for every `decided` disposition of that root): look the `disposition_id` up in `target_dispositions`. **Present:** the journal step committed; set `applied`. **Absent and the current state digest equals the decided one:** run step (2), then (3). **Otherwise:** set `lapsed`; it is never applied. `run_abandon` is entirely in the ledger and is one transaction. Tests (M5a-09 additions): SIGKILL between (1) and (2), **between (2) and (3)** (completion must find the id and only mark `applied`, never apply twice), and after (3); a digest change between (1) and completion yields `lapsed`.

New refusal codes `DISPOSITION_STALE`, `DISPOSITION_PRECONDITION`, `DISPOSITION_NOT_APPLICABLE` (internal, generic external mapping, INV-44, O-6); reads of disposition contexts need an Operator-scoped read session (D-044 item 3).
