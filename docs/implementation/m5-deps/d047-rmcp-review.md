## Protocol and closure gates

A stand-alone probe built with the candidate features negotiated 2025-11-25 for an exact request and offered only 2025-11-25 for initialize requests proposing 2024-11-05 and 2026-07-28. Before any initialize exchange, the same stateless methods declaring 2025-11-25 succeeded. The SDK also documents that it may serve regular requests before receiving the initialized notification after a completed initialize response. **A version allow-list alone therefore does not pin the 2025-11-25 handshake.** Before an effect shim can be integrated, enforce the legacy lifecycle using the SDK’s typed transport or handlers and test that stateless opening messages, tool requests before initialization completes and unsupported versions cannot forward effects. Use the SDK for framing and negotiation. Treat transport identity and lifecycle flags as protocol data. Writ socket admission and broker approval checks govern effects. ### Concrete lifecycle requirements for the next eligible candidate

Source review of 3.9.0 found that `serve_inner` spawns request and notification callbacks separately. A mutex around `Lifecycle` serializes callback execution but cannot preserve the order in which the SDK received those messages. A late callback for a pre-initialization tool could observe readiness from a later notification. The SDK also delays cancellation of in-flight handlers during EOF response draining. [Server startup and negotiation](https://github.com/modelcontextprotocol/rust-sdk/blob/5596a8a0bba2a1ec5519cc855cdadf23e4dcecdc/crates/rmcp/src/service/server.rs#L551) · [Service dispatch and drain](https://github.com/modelcontextprotocol/rust-sdk/blob/5596a8a0bba2a1ec5519cc855cdadf23e4dcecdc/crates/rmcp/src/service.rs#L1565)

- Use one lifecycle per connection. Enforce wire order at the SDK's sequential typed transport receive boundary or through an upstream ordered dispatch API. Advance only after the successful initialize response selecting 2025-11-25 has been sent and a subsequent typed initialized notification has arrived. Refuse pre-ready tool messages even if their callbacks run later. Close on duplicate lifecycle messages, shutdown and disconnect before the SDK drains responses. Confirm how the eligible SDK exposes terminal protocol failures. The 3.9.0 async stdio decoder handles some malformed frames internally before returning the next typed message. [SDK transport contract](https://github.com/modelcontextprotocol/rust-sdk/blob/5596a8a0bba2a1ec5519cc855cdadf23e4dcecdc/crates/rmcp/src/transport.rs#L125) · [Async stdio receive](https://github.com/modelcontextprotocol/rust-sdk/blob/5596a8a0bba2a1ec5519cc855cdadf23e4dcecdc/crates/rmcp/src/transport/async_rw.rs#L252)
- Pin `get_info().protocol_version` and `supported_protocol_versions()` to 2025-11-25. Guard `list_tools` and `call_tool` with the typed admission result and current connection state. Keep other routes incapable of effect dispatch. Allow-list tool names and validate arguments before forwarding. Treat init metadata and connection identifiers as untrusted protocol data. Connect only through the Writ host RPC path, verify the configured service uid by peer credentials before any send and preserve broker authorization. [Typed handler contract](https://github.com/modelcontextprotocol/rust-sdk/blob/5596a8a0bba2a1ec5519cc855cdadf23e4dcecdc/crates/rmcp/src/handler/server.rs#L583) · [Writ local RPC contract](../M5-INTERFACES.md#j-2-local-rpc-over-unix-sockets-review-m-6-l-1-l-4-l-5)
- Bind cancellation to the SDK request context and connection lifecycle. Cancel or refuse work still pending before RPC submission. For an already submitted request, keep the broker receipt or uncertain outcome semantics and avoid automatic replay. Reject duplicate in-flight MCP request IDs and preserve the single in-flight rule of each Writ RPC connection.
- Test both `tools/list` and `tools/call` over real SDK stdio with a dispatch counter and deterministic scheduling barriers. Cover the pinned handshake, SDK fallback to the pinned revision for other initialize proposals, unsupported inline revisions, stateless and pre-ready calls, a tool received before initialization completes whose handler is delayed until after the initialized notification, back-to-back notification and tool messages, duplicate lifecycle messages and in-flight IDs, cancelled and disconnected pending calls, and a fresh connection after closure. Assert zero broker forwards for all refused calls and for `tools/list`. Assert one forward for each accepted effect-bearing `tools/call`.
