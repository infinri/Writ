# M4 shared interfaces (lead-owned; D-040, D-041)

Binding for every M4 worker. Changes only by the lead. Design background: [M4-START-PLAN](M4-START-PLAN.md) sections 2..6. Status: **specified; contracts (M4-01) in implementation; independent review required before any consumer is integrated.**

## Layering

| Layer | Crate / module | May depend on | Must not contain |
|---|---|---|---|
| Kernel | `writ-kernel` | unchanged | anything M4 |
| Broker logic (storage-independent) | `writ-broker`: new `human` (verifier boundary types and trait), `approval` (records, state machines, checks), `acceptance` (signoff use-time checks), `refusal` (codes) | kernel, existing deps | network, HTTP, Tokio, WebAuthn library, randomness source, SQL |
| Persistence | `writ-ledger-sqlite`: `schema_v6.sql`, `approval_store.rs` | broker, rusqlite | HTTP, WebAuthn |
| Approval channel | new `writ-approval` crate | broker, webauthn-rs (D-041), hyper HTTP/1 + tokio (D-041) | kernel internals beyond broker APIs |

## I-1 Subjects, roles and the verifier boundary (`broker::human`)

- `SubjectId { issuer: String, subject: String }`: stable issuer or realm plus subject; never a display name. `PrincipalKind { Human, Service }` on every subject.
- `Permission { Approver, SignoffAuthority, Operator, Revoker }`, each granted per (tenant, project) scope (`RoleAssignment { subject, kind, permission, tenant_id, project_id, granted_at, revoked_at }`). Services can hold only `Operator` for declared automation operations; never `Approver` or `SignoffAuthority` (O-8).
- `trait HumanVerifier` (implemented in `writ-approval`; test implementations only in non-shipping test code):
  - `begin(&self, subject: &SubjectId, credentials: &[StoredCredential]) -> Result<CeremonyStart, VerifierError>`: `CeremonyStart { client_options: Vec<u8> /* sent to the page */, state: CeremonyState /* opaque bytes, persisted only in the ledger */, challenge_digest: Digest }`.
  - `finish(&self, state: &CeremonyState, response: &[u8], credentials: &[StoredCredential]) -> Result<VerifiedAssertion, VerifierError>`: `VerifiedAssertion { subject, credential_id, user_verified: true /* required */, method: "webauthn-passkey", credential_update: Option<CredentialUpdate> }`.
  - Only active credentials are passed in (revocation is the ledger lookup). Ceremony state never leaves the server and is never accepted from the client (D-041).
- `StoredCredential { credential_id, subject, public_material: Vec<u8> /* library-serialized passkey */, status: Active | Revoked, enrolled_at, enrolled_by }`.

## I-2 Challenges (O-3)

A challenge row binds, server-side: challenge id, `challenge_digest`, ceremony state, subject and allowed credential ids, operation (`Approve | Deny | Revoke | Signoff | Enroll | RoleChange`), verdict, tenant, project, target id (approval request, grant, signoff or subject), complete immutable context fingerprint (D-006 canonical digest of the stored target context as displayed), policy bundle digest and relevant revision, issued_at, expires_at = min(issued_at + 120 s, target expiry), idempotency key, status `issued | consumed | expired`. Consumption is in the same transaction as the durable decision. An identical retry (same idempotency key and same assertion outcome) after an unknown commit replays the original result; anything else with a consumed challenge is refused. Sessions (read-only inbox, at most 15 minutes) never authorize a state change.

## I-3 Approval records and state machine (`broker::approval`)

- `ApprovalRequest` (immutable once stored): request id (kernel `approval_request_id`), tenant, project, requester principal, agent id, delegation chain, action kind, canonical resource id, action digest, capabilities, policy bundle digest, request fingerprint, created_at, expires_at, `required_approvers: 1` (O-9; a policy needing more is refused `APPROVAL_QUORUM_UNSUPPORTED`). Status `pending -> approved | denied | expired`; `denied` and `expired` are terminal; `approved` produces exactly one grant.
- Created by `Broker::execute` when the use-time decision is `require_approval` and no grant is presented (agent still receives `APPROVAL_REQUIRED`; the request id goes only to the human channel).
- `ApprovalDecision { request_id, verdict, subject, credential_id, channel /* from listener config */, decided_at, challenge_id, provenance_version: "writ-provenance-2" }`; room for several decision rows per request, but one suffices and no quorum is implied.
- Separation (O-7): approver subject differs from requester principal, agent and every delegation-chain member; checked by `SubjectId`, and across all credentials and roles of the same subject.

## I-4 Revocation (O-5)

`Revocation { target: Grant(id) | Signoff(id) | Credential(id) | Subject(SubjectId) | Role(assignment id), by: SubjectId, at, reason, challenge_id }`. Ledger status is authoritative and rechecked at T-reserve, T-dispatch and promotion: before reserve refuse; after reserve before dispatch refuse with the receipt kept `reserved` and its grant use kept; after dispatch nothing is undone and the revocation is recorded as after-dispatch. Never refund, replenish or substitute.

## I-5 Signoff (O-4) and the amended record contract

- `Signoff { signoff_id, tenant, project, task, workflow, transition (from, to), acceptance_record_id, criterion_id, artifact_snapshot_id, artifact_digest, acceptance_policy_id, version, bundle digest, state_revision, issued_at, expires_at, subject, credential_id, challenge_id, provenance_version }`, stored in the ledger; consumed single-use ledger-wide atomically with the promotion.
- `authenticated-acceptance-record/2`: as `/1`, plus per-evaluation `signoff_id`, required exactly for trust `H` (and `attestation_id` exactly for trust `M`); `/1` records keep refusing human criteria (`ACCEPTANCE_HUMAN_UNAVAILABLE`), never reinterpreted; mechanical-only `/1` records stay valid.
- Use time (`check_use`, inside the promotion transaction): signoff exists in scope, provenance intact, binding equals record and requirements and current state, not revoked (signoff, credential, subject, role), fresh at trusted time, signer holds `SignoffAuthority` for the scope, signer is not the requester, agent, delegation chain, nor the subject who changed the artifact or acceptance policy for this revision, never consumed.

## I-6 Refusal codes (O-6; internal, external mapping generic)

`APPROVAL_REQUEST_UNKNOWN`, `APPROVAL_REQUEST_CLOSED`, `APPROVAL_REQUEST_EXPIRED`, `APPROVAL_QUORUM_UNSUPPORTED`, `CHALLENGE_INVALID` (unknown, consumed, expired or binding mismatch; diagnostic says which), `ASSERTION_INVALID` (verifier refusal; diagnostic from the library category only), `CREDENTIAL_REVOKED`, `SUBJECT_REVOKED`, `PERMISSION_MISSING`, `SEPARATION_VIOLATED`, `SERVICE_NOT_PERMITTED`, `ENROLLMENT_UNSUPPORTED`, `GRANT_REVOKED`, `SIGNOFF_UNKNOWN`, `SIGNOFF_REVOKED`, `SIGNOFF_MISMATCH`, `SIGNOFF_EXPIRED`, `SIGNOFF_CONSUMED`. Every new code maps to the kernel's generic external refusal.

## I-7 Persistence (`writ-ledger-6`, tables only)

Additions during remediation (D-042, `writ-ledger-6` still unreleased, amended in place): `approval_grants` (X1 link), `registrations` (X8 server-held registration ceremony), `signoff_requests` (X7 stored promotion context; `deadline_at`, D-043 Y1), `signoffs.exclusions`, challenge status `refused` with `refusal_code`, challenge `rp_id` and `origin` (configured channel), challenge `signoff_expires_at` (D-043 Y1), `ledger_sequence` kinds `expiry` and role change. `subjects`, `credentials`, `role_assignments`, `approval_requests`, `approval_decisions`, `challenges`, `revocations`, `signoffs`, `consumed_signoffs`, `approval_events` (provenance v2, no credential material). `SqliteLedger::open` accepts only `writ-ledger-6`; `SqliteLedger::upgrade` from exact `-3`, `-4`, `-5` keeps every row; at upgrade every pre-M4 grant becomes non-executable (O-14) by a recorded marker (no row rewritten or deleted; reservation and use history kept; dispatched or completed receipts keep reconciliation and replay). Enrollment and recovery: only the documented administrative ceremony (M4-08); otherwise `ENROLLMENT_UNSUPPORTED`.

## I-8 Ordering evidence (CO-PROP-02)

Every promotion, administrative operation and revocation commits a row in one ledger-wide monotonic sequence (`ledger_seq`, assigned inside the transaction), so tests establish the actual order of concurrent invalidations and commits and check each exactly.

## Security review of the approval ledger (2026-11-14; remediated under D-042, E-075; independent re-review: S1..S8 fixed)

- **S1 HIGH (G1 confirmed):** `GrantService::approve` (broker/src/grants.rs) mints executable `writ-provenance-1` grants on `writ-ledger-6` through `insert_grant` with any `ApprovalAuthority` implementation; such grants ignore subject, credential and role revocation, and the caller may take the `approval/<rid>` label first (the real M4 approval then fails `GRANT_REF_IN_USE`). No production binary calls it today (only the M3 closure adapter). - **S3 MEDIUM:** signoff parties (`CeremonyOp::Signoff.parties`) come from caller input, not the ledger, and are not fingerprinted; `consume_signoff` checks neither separation nor role. Fix: read parties from the stored request/record at signing; M4-06 use-time checks mandatory before any consumer.

## Remediation design (D-042, lead, 2026-11-14; binding for the remediation workers)

- **X1 executability on `writ-ledger-6` (S1, S2):** a grant is executable only when an `approval_grants` row links it to an `approved` approval request, its `approval_decisions` row and its consumed challenge, all written by the ledger's own ceremony transaction (a private function of the SQLite crate, reachable only through `ApprovalLedger::finish_ceremony`). T-reserve and T-dispatch re-read that link and the current subject, credential and role status inside their transactions. `ExecuteLedger::insert_grant` on `-6` refuses every provenance (`writ-provenance-1` is the legacy path, `-2` is minted only internally) and every label beginning with `approval/`; `GrantService::approve` therefore refuses on `-6`. The public constructor chain of S2 (`LedgerCapability::for_ledger_implementation`, `ApprovalDecision::from_stored`, `NewGrant::for_decision`) is removed or made unable to produce anything a ledger treats as executable; an external-crate integration test (`persistence/sqlite/tests/`) proves it.
- **X2 agent binding (S8):** the grant binding includes the request's agent id; reserve refuses a different agent of the same principal (existing generic grant refusal; internal diagnostic names the agent mismatch).
- **X3 replay identity (S4):** replay requires equality of subject, credential, operation, verdict, target id and complete context fingerprint with the original consumed challenge; any difference is `CHALLENGE_INVALID` (diagnostic `binding mismatch`), never the earlier result.
- **X4 refusal burns the challenge (S6):** a terminal refusal of an identified ceremony (verifier refusal, separation, permission, revoked, closed target) commits challenge status `refused` with the refusal code in the same transaction; a retry with that challenge is `CHALLENGE_INVALID` (`consumed`). If that commit fails or is uncertain the ceremony result is the storage refusal (fail closed) and the challenge is never treated as fresh by a later ceremony (status read inside the next transaction). An identical retry of an already committed successful decision still replays it. `writ-ledger-6` is not yet accepted, so the lead amends `schema_v6.sql` (new status value) without a new version; no released ledger carries it.
- **X5 revoker scope (S7):** `RoleAssignment` scope `(tenant, project)` with `*` only where explicitly granted: `(*, *)` contains every scope; `(t, *)` contains every project of tenant `t`; `(t, p)` contains only itself; containment is never inferred across tenants and `*` in a target is never matched by a narrower assignment. **Role change:** operation `RoleChange` (grant or revoke one assignment) needs a fresh user-verified ceremony by a human holding `Operator` over a scope containing the assignment's scope; a subject never changes its own assignments; services never receive `Approver` or `SignoffAuthority`; each change writes provenance (`approval_events`) and a `ledger_sequence` row in its transaction.
- **X6 ordering (S8):** `expire`, the role change and every remaining state-changing write named in I-8 commit a `ledger_sequence` row in the same transaction.
- **X7 signoff parties (S3):** at `begin` and at `finish` the signoff exclusions are read from the ledger inside the transaction: the requester and agent of the stored promotion context, linked requester identities from enrollment records, and the artifact and policy changers from durable administrative events for the exact revision; they are part of the signoff context and its fingerprint, and the page displays them. Caller input may only add exclusions. Delegation chains are not stored by M3 sealed ingress (G4): the context records `delegation_chain: unavailable`, and separation is documented as covering requester, agent and linked identities only; nothing claims full delegation-chain separation.
- **X8 enrollment (S5):** `NewEnrollment` carries a verified registration result (a value any linking code can build through an `ApprovalChannel` of its own since the M1 fix, so it carries no authority by itself: the ledger accepts it only when it equals what its own server-held registration row recorded, bound to subject, RP id and origin, see "Configured approval channel" below); raw public material is refused. `bootstrap_administrator` moves to a separate entry point that opens the ledger path through the canonical-identity and sidecar ownership-lock protocol (the same `OwnerLock` and lifecycle gate as normal service), refuses when any owner holds the lock and refuses when any subject already exists.

## Configured approval channel and review findings of `4e5d196` (D-040..D-042; worker W-D)

Independent security review of `4e5d196` (M1 MEDIUM; L1..L8 LOW). These enforce existing requirements (O-2, O-3, X1, X4, G4); no new trust-boundary decision.

- **M1 configured approval channel (fixed).** Ceremony and registration calls (`CeremonyBegin`, `CeremonyFinish`, `RegistrationBegin`, `RegistrationFinish`) no longer take a verifier or a channel identity. An `ApprovalChannel` (`broker::human`: the human and registration verifier, the relying party read once when it is built, the channel identity recorded on decisions) is attached once to the owned ledger; a channel whose assertion verifier and registration verifier report different relying parties is never built (N1: `HumanVerifier::relying_party`, `ApprovalChannel::new` refuses) (`SqliteLedger::with_approval_channel`, `BootstrapSession::with_approval_channel`; consuming, so no holder of a shared reference can set or replace it; a second configuration is refused). A ledger without a channel refuses every ceremony and registration (`ASSERTION_INVALID`, verifier unavailable; nothing burnt). Challenges record the RP id and origin they were issued for (`challenges.rp_id`, `challenges.origin`, amended in the unreleased `schema_v6.sql`; registration rows already did); a finish under a channel with another RP id or origin is refused before the verifier sees the ceremony state (`CHALLENGE_INVALID`, diagnostic `approval channel mismatch`; registration `ENROLLMENT_UNSUPPORTED`) and the challenge or row is burnt (X4). `VerifierCapability` has no public constructor: the channel lends it by reference to `HumanVerifier::finish` and `RegistrationVerifier::finish_registration` for the duration of the call (its test constructor is `#[cfg(test)] pub(crate)` in the broker). `LedgerCapability::for_ledger_implementation` stays public, because the SQLite ledger is another crate and Rust cannot restrict callers across crates without a feature; `broker/tests/trusted_constructors.rs` confines it to the SQLite ledger and test code, and nothing built with it is accepted by a ledger as authority (X1: the ledger reads its own rows). Regression: `persistence/sqlite/tests/grant_authority.rs` (a ledger without a channel refuses every ceremony and registration; a stub verifier passed from that external crate cannot be configured twice and, configured on a later open for another relying party, cannot finish a challenge or registration row issued under the real channel; the S2 chain now mints its assertion through a stub channel and is still refused).
- **What the configured-channel rule guarantees, and what it does not.** It guarantees that a running approval service uses exactly the verifier and relying party it was opened with; that no ceremony call can substitute a verifier; that a ledger opened without a channel performs no ceremony; and that a challenge or registration row issued for one RP id and origin is never finished under another. It does not authenticate the verifier: whoever opens the ledger chooses the channel. **Code that links `writ-broker`, `writ-ledger-sqlite` or `writ-approval` in process and opens the ledger is inside the trust boundary, equivalent to access to the ledger file** (which already allows reading and writing every row, and the one-shot bootstrap, M4-ENROLLMENT-CEREMONY section 5): such code can configure a stub verifier that claims the real RP id and origin, and can mint `VerifiedAssertion` and `VerifiedRegistration` values through a stub channel of its own. The protection against a second process is the sidecar ownership lock (only one owner opens the ledger at a time); the protection of values minted outside the ledger is X1 and X8 (the ledger accepts only its own rows and its own ceremony transaction). Deploying only reviewed binaries that wire the `writ-approval` passkey verifier is an operational requirement of the local profile.
- **L1 listener refusal codes (fixed).** A refused `/ceremony/begin` answers one generic `refused` to the page (a page session is not an authentication); the specific code stays in the ledger's refusal audit. `/ceremony/finish` keeps the internal code (O-6). Documented exposure: a successful begin returns the verifier's options, including WebAuthn `allowCredentials` (the subject's credential ids), to any loopback client holding a page session that names an enrolled, permitted subject; this is inherent to the non-discoverable passkey flow and is bounded by L2 and the loopback-only binding. A begin still distinguishes success from refusal. Regression: `approval/tests/listener.rs` `a_refused_begin_answers_one_generic_refusal`.
- **L2 outstanding challenges (fixed).** The listener caps issued, unexpired challenges across all sessions (`Limits::max_outstanding`, default 32, each counted for at most the 120 s challenge lifetime, reserved under the session lock before the ledger is asked) besides `max_pending` per session; when `max_sessions` is reached only a session without a pending ceremony is evicted, and if every session has one the new session is refused (503, fail closed). Accepted local limitation (N2): any loopback client that can open a page session and names an enrolled, permitted subject can fill the global cap and so block other ceremonies. Repeated hostile loopback requests can sustain this denial of service: 120 s bounds one challenge, not the overall outage (D-043). It fails closed and is a local denial of service only. Regressions: `outstanding_challenges_are_capped_across_sessions`, `a_session_with_a_pending_ceremony_is_never_evicted`.
- **L3 signoff lifetime (superseded by D-043 item 2 and Y1, implemented by W-E).** Formerly the caller chose a signoff's `expires_at`. Now the ledger computes it at begin (at most 600 s); see Y1.
- **L4 delegation chain (fixed).** Approval-request contexts record `delegation_chain: "unavailable"` exactly as signoff contexts do (never an empty list that reads as "no delegation"); `NewApprovalRequest` and `Parties` carry no chain field, and the `approval_separation` and `Parties` documentation states that separation covers requester, agent and linked identities only (G4). Request fingerprints change; `writ-ledger-6` is unreleased. Regression: the stored-member assertion in `approval::tests::every_displayed_field_is_fingerprinted_including_the_action_body`; the ledger refuses to load a stored request context with any other `delegation_chain` value.
- **L5 broker-side approval link (fixed).** `grants::provenance_intact` treats a `writ-provenance-2` grant without an `ApprovalLink` as not intact, so the broker itself refuses it at T-reserve and T-dispatch (diagnostic `provenance`) whatever `GrantLedger` read it; provenance-1 grants on M3 ledgers are unchanged. Regression: `grants::tests::a_provenance_2_grant_without_an_approval_link_is_never_executable` (fails with the check removed).
- **L6 transient verifier outage (fixed).** A verifier answer `Unavailable` (and a ledger without a channel) is not a terminal refusal: the ceremony answers `ASSERTION_INVALID` (verifier unavailable) without burning the challenge or registration row, which stays issued, single use and expiring; the listener keeps the pending entry and answers `unavailable`. Regressions: `d042_tests::l6_an_unavailable_verifier_never_burns_the_challenge` (fails with the old burn), the registration case in `m4_approval_tests::registration_is_verified_bound_and_single_use`, and `a_verifier_outage_keeps_the_pending_ceremony`.
- **L7 legacy label collision (documented).** A pre-M4 grant carried over by the upgrade keeps its label; if it already occupies `approval/<request id>`, the M4 approval of that request cannot insert its grant (`GRANT_REF_IN_USE`, the challenge is burnt) and the request stays pending until it expires. This is denial of service only: the legacy grant is non-executable (O-14 marker) and nothing is minted or substituted. **Explicit fail-closed migration and recovery obligation (D-043):** until a reviewed migration renames or retires such rows, the collision stays refused as above (never resolved by reusing, overwriting or substituting the legacy row), and any recovery procedure for an affected request must keep it fail closed; the obligation stays open and tracked until that migration exists.
- **L8 registration rows (documented).** A registration row is bound to subject, RP id, origin, operation and expiry, not to the administrator who will later enroll it; any caller with access to the serving ledger's `RegistrationLedger` can open rows. There is no HTTP route for registration (the listener serves approve and deny only), and an enrollment still needs a fresh `Enroll` ceremony by an operator in the global scope that binds the registered credential, so an unbound row grants nothing; binding rows to an operator is future M4-08 work.

## M4 completion design (D-043, lead, 2026-11-14; binding for the completion workers)

- **Y1 signoff expiry:** `SIGNOFF_MAX_LIFETIME_SECONDS = 600`. At ceremony begin the ledger computes `expires_at = min(now + 600, policy maximum if any, trusted promotion-context deadline, record validity deadline, caller-requested expiry if supplied)` on trusted time inside the begin transaction; refused (`SIGNOFF_EXPIRED` for an already passed deadline, `SIGNOFF_MISMATCH` diagnostic `invalid interval` otherwise) when `expires_at <= now`. The effective expiry is stored with the challenge, is a member of the displayed context and fingerprint, and the signoff row takes exactly that value at finish (finish never recomputes it; the challenge lifetime stays `min(120 s, expires_at)`). Promotion rechecks `now < expires_at` on trusted time (with the trusted-time floor, so a clock rollback cannot revive an expired signoff). Stored signoffs with `expires_at - issued_at > 600` are refused at use (`SIGNOFF_EXPIRED`, diagnostic `exceeds maximum lifetime`), never rewritten. No extension operation exists.
  - *Implementation (W-E):* `writ_broker::approval::signoff_expiry` and `SIGNOFF_MAX_LIFETIME_SECONDS`; `CeremonyOp::Signoff.requested_expires_at` (optional, only shortens; never read at finish); `NewSignoff` no longer carries an expiry: the effective one is `SignoffFields.expires_at`, passed to `context_with`/`displayed`/`signoff_binding`/`Signoff::sign`. Policy maximum: none (the acceptance requirement set has no lifetime field). **Y2 registration binding (ledger; lead decision within D-043 item 4: rows only from an authenticated operator ceremony).**

- New ceremony operation `RegistrationStart` (`ChallengeOperation::RegistrationStart`, stored `registration_start`, closed verdict `start`); `CeremonyOp::RegistrationStart { subject, operator, operator_session }`; result `CeremonyResult::RegistrationStarted { registration: IssuedRegistration }`. Target `registration-start:<subject target id>:<len rp_id>:<rp_id>:<origin>` in the global scope, policy `none`. Displayed and fingerprinted context (`registration_start_context`, `writ.registration-start-context.v1`): operator, intended subject, operation `enroll`, RP id and origin of the configured channel, `registration_lifetime_seconds` 600 (the row expires 600 s after the start ceremony commits). Roles and linked identities are not part of it: they are displayed and bound by the later `Enroll` ceremony. The page session id is not displayed or fingerprinted.
- Begin and finish require: a configured channel (otherwise `ASSERTION_INVALID`, verifier unavailable); an acting subject equal to the operation's `operator` (`ENROLLMENT_UNSUPPORTED`); an active human with `Operator` over a scope containing (`*`, `*`) and an active credential (`PERMISSION_MISSING`, `SERVICE_NOT_PERMITTED`, `SUBJECT_REVOKED`, `CREDENTIAL_REVOKED`); a bootstrapped ledger, a well-formed, not yet existing subject and a non-empty session (`ENROLLMENT_UNSUPPORTED`); never self, under any issuer (`SEPARATION_VIOLATED`).
- The finish consumes the challenge in the same transaction that calls the channel's registration begin and inserts the row (`registration_id` `reg-<challenge id>`, operation `enroll`, operator, session, subject, RP id, origin, `started_by` = challenge id, creation options, expiry 600 s), an `approval_events` row `registration_started` and a `ledger_sequence` row of kind `registration`. X3: an identical retry replays the same row and options; a retry with another target or fingerprint is `CHALLENGE_INVALID` (binding mismatch), and so is a retry from another page session (the session is not fingerprinted, so the replay compares it with the row). X4: a terminal refusal burns the challenge. L6: an unavailable verifier (assertion or registration begin) burns nothing.
- `RegistrationLedger::begin_registration` on the serving ledger always refuses (`ENROLLMENT_UNSUPPORTED`): no row without a consumed start ceremony. `BootstrapSession` is unchanged (one shot, no operator session).
- Schema: `registrations` gains `operator_issuer`, `operator_subject`, `operator_session`, `started_by` (UNIQUE) and `client_options`; CHECKs: present exactly for `enroll` rows (`started_by` too), absent for `bootstrap` rows. `challenges.operation` admits `registration_start`, `approval_events.kind` `registration_started`, `ledger_sequence.kind` `registration`.
- `finish_registration` burns the row (`ENROLLMENT_UNSUPPORTED`) unless the same operator and session finish it. The `Enroll` ceremony (begin and finish) refuses (`ENROLLMENT_UNSUPPORTED`; burnt at finish) unless the row's session equals `CeremonyOp::Enroll.operator_session`, the actor is the row's operator, the row's RP id and origin equal the configured channel's, and (unchanged) the row is the subject's, registered, unexpired and single use. L8 is superseded by Y2.
- Reads for the pages (`ApprovalLedger`): `ceremony_context(op, now)` returns the context and binding a begin at the same trusted time computes (the same `target` function, including Y1's `SignoffExpiry::Compute(now)`; R6 checked: the context's canonical digest equals the binding's fingerprint); `pending_signoff(signoff_id, now)` builds a `NewSignoff` from `signoff_requests`, the workflow and the active acceptance policy only (`None` when unknown or already signed); it carries no expiry.

**Signoff expiry on the page (Y1 integration).** The signoff page reads `ceremony_context` (effective expiry E computed by the ledger exactly as a begin would), pins E as `requested_expires_at`, re-reads the context (the same fingerprint, else no page) and displays it. A later begin computes `min(its now + 600 s, trusted deadline, E) = E`; if a deadline moved, the context differs and the begin is refused as a stale display. The page never shows one expiry and signs another. Regression: `m4_signoff_tests::y1_the_signoff_page_displays_exactly_the_expiry_the_begin_fixes` (an unpinned later begin would bind another fingerprint).

**Routes and form fields (stable for W-G).** Every route keeps the existing protections: loopback bind, exact `Host` and `Origin` (required on every `POST`), `application/x-www-form-urlencoded` bodies within the bounds, CSRF token per page session, `HttpOnly` `SameSite=Strict` cookie `writ_session`, strict CSP (no inline script or style, `form-action 'none'`), escaped untrusted text, read-only sessions of at most 15 minutes, fresh ceremony and idempotency key per state change, channel from configuration.

**Listener behaviour.** The operation, target, idempotency key, verified registration and page-session id (random, not secret, distinct from the cookie) are server-side session state. Begin rechecks the current fingerprint (request, or `ceremony_context`) against the displayed one (409 stale display). A registration start and an enrollment are begun only for their operator (otherwise generic `refused`, nothing sent to the ledger; the ledger checks it again). Refusals of `/ceremony/begin` and `/prepare` are one generic `refused`; an unknown signoff id is one generic not-found page without a session; `/ceremony/finish` and `/registration/finish` keep the internal code (O-6); a verifier outage answers `unavailable` and keeps the pending entry (L6). Registration rows count toward `max_pending` and `max_outstanding` for their 600 s lifetime, and a session holding one is never evicted (L2); repeated hostile loopback requests can sustain that denial of service (N2).

**Security re-review of `041e52e` (LOW-1..LOW-3) and their disposition.**

- **LOW-1 session fixation through another localhost port (fixed).** Cookies are not scoped by port and `SameSite` treats `localhost:<other port>` as same-site, so a page served from another local port could plant a `writ_session` cookie or drive requests that carry it. Every page that creates or uses a session (`/request/<id>`, `/signoff/<id>`, `/revoke`, `/role`, `/enroll`, `/view`) is served only with `Sec-Fetch-Site: same-origin` (a navigation from this listener's pages) or `none` (a user-initiated navigation: address bar, bookmark, reload); every `POST` needs `same-origin` or `none`. `same-site`, `cross-site` and a missing header are refused (403 `fetch site`): fail closed, so a client without Fetch Metadata (a non-browser client or an old browser) cannot use the pages; current browsers send the header on every navigation and `fetch`. Static assets need no session and are not checked. Regressions: `approval/tests/listener.rs` `a_cookie_planted_from_another_port_is_refused` and the browser flow "revoke page refuses a wrong CSRF token and a wrong origin" (Sec-Fetch-Site same-site refused). **Tightened after the re-review of `398b8f1`:** `GET /view` and every `POST` require exactly `same-origin` (they are reached only by this origin's own script), so a user-initiated reload or bookmark (`none`) after a cookie overwrite from another port is refused too; session-creating pages still accept `none` for direct navigation. Test: `a_cookie_planted_from_another_port_is_refused`.
- **LOW-2 context oracle (accepted for the local profile, documented).** `/prepare` and `/view` (and `/request/<id>`, `/signoff/<id>`) let any loopback client that can open a page session read the displayed context of a named subject, credential, role assignment, grant or signoff (an existence and content oracle over these records). This is the R6 display itself: the page must show the stored context before any assertion. Restricting it would need an operator-authenticated page session (a separate assertion before `/prepare`), which is not a cheap change and would add a ceremony type; it is not done. The exposure is bounded by the loopback-only binding and the L2 session bounds, matches the documented L1 exposure of `allowCredentials`, and reveals no credential material or authority.
- **LOW-3 unbounded ledger growth (documented, carried obligation).** Refused begins and finishes write audit rows, and issued, expired, refused and consumed challenge rows and registration rows are retained (history and replay evidence), so a hostile loopback client can grow the ledger file without bound: a local denial of service on disk. Retention and compaction of audit, challenge and registration history (never of decision, grant, signoff, revocation or ordering evidence) is a carried obligation for a later milestone; nothing is deleted today.
