## Amended contracts (D-033 item 4)

Machine-readable drafts: [`evaluator-registry-entry.schema.json`](../contracts/proposed/evaluator-registry-entry.schema.json), [`runner-attestation.schema.json`](../contracts/proposed/runner-attestation.schema.json), [`evaluation-record-scope.schema.json`](../contracts/proposed/evaluation-record-scope.schema.json), with valid examples in `docs/contracts/proposed/examples/`. All are closed objects (unknown members invalid) with a versioned `contract_version`; ids, names, versions, digests (`sha256:` plus 64 lowercase hex), strict UTC whole-second times (D-022) and revisions (0..2^53-1) have exact patterns.

**Evaluator registry entry:** identity (`evaluator_id`, `evaluator_version`), `class` and fixed `trust` (mechanical M, evidence E, model_assisted MA, human H), `implementation_digest`, `environment_digest`, **registered `command` (`command_id`, `command_digest`), required for mechanical evaluators**, `attestation` (`alg`, `key_id`), `criteria` it may satisfy, **explicit `scope` (`tenant_id`, `project_id`); the global marker is deferred until its authorization semantics exist**, publisher fields, `registry_revision`, `status` (`active` or `revoked` with `revoked_at`).

**Runner attestation:** `purpose` `writ.runner-attestation.v1` (domain separation), `attestation_id`; the exact acceptance context (`tenant_id`, `project_id`, `task_id`, `workflow_id`, `transition`, `artifact_snapshot_id`, `artifact_digest`, `canonical_target`, `acceptance_policy_id`, `acceptance_policy_version`, `acceptance_policy_bundle_sha`, `state_revision`, `acceptance_record_id`, `criterion_id`); evaluator binding (`evaluator_id`, `evaluator_version`, `implementation_digest`, `environment_digest`, `registry_revision`); `command_id` and `command_digest`; `input_digests`, `evidence_digests`, `exit_status`, `output_digest`; `started_at`, `finished_at`, `fresh_until`; `auth` (`alg`, `key_id`, `mac`).

**Authenticated bytes and algorithm policy:** the MAC input is the UTF-8 D-006 canonical JSON of the attestation with `auth.mac` removed (so `contract_version`, `purpose`, `alg` and `key_id` are authenticated). `alg` is a closed list, currently only `hmac-sha256`: an HMAC is a **MAC with a shared runner key, not a public-key signature**, so anyone holding the key (runner and verifier) can produce tags; a public-key scheme would be a later contract version. Unknown algorithm, unknown `key_id`, a `key_id` or `alg` different from the registry entry's `attestation` at the bound `registry_revision`, or a key of another purpose, fails closed. Key material comes only from the trusted key provider under purpose `runner` (D-033 item 1); the kernel never verifies MACs.

**Use-time checks (code, M3-05 and M3-07):** every bound context field equals the protected transition being promoted; the registry entry is active at use time, its digests and command equal the attestation's, and its scope contains the tenant and project; `exit_status` and `output_digest` satisfy the criterion; `fresh_until` is after trusted effective time (M3-TRUSTED-TIME); the snapshot rule below holds.

**Consumption (approved choice):** single consumption **ledger-wide per `attestation_id`**, atomic with the protected promotion in one fenced transaction; an identical retry of the same promotion is idempotent; use for another acceptance record or criterion is refused; verification alone never consumes.

**EvaluationRecord scope (historical; superseded for the authorization path by D-038 item 1, see below):** the same context and evaluator binding, `evaluator_trust`, `status`, `attestation_ref` (required for trust M), `evidence_digests`, `issued_at`, `fresh_until`, `mode` (`governed` or `advisory`; advisory never satisfies a protected transition, INV-39). Proposed as an amendment of `docs/contracts/evaluation-record.schema.json`.

**Human mandatory criteria** stay unavailable (refused) until authenticated signoff exists (M4); there is no interim bypass.

## Structural schemas versus semantic validation (owner decision, 2026-11-12)

**JSON Schema is a structural check only.** The schemas in `docs/contracts/proposed/` fix shapes, types and patterns; they cannot express calendar validity, kernel resource-id rules, cross-field binding or time order. For example, JSON Schema alone accepts `2026-02-30T00:00:00Z`, `2026-13-01T00:00:00Z` and `2026-11-07T24:00:00Z` (pinned by `test_invalid_calendar_dates_pass_json_schema_alone`). **Every trusted ingestion path of these contracts performs the semantic checks in `broker::contracts`** (`broker/src/contracts.rs`; implemented, M3-02 follow-up of 2026-11-12; no ingestion path exists yet, the first are M3-05 and M3-07): the only constructors of `RegistryEntry`, `RunnerAttestation` and `EvaluationRecordScope` are their `validate` functions, so a consumer that takes those types (M3-05, M3-07) cannot receive an unvalidated document. (`EvaluationRecordScope` has no ingestion path and gets none: D-038 item 1; its validator and tests are kept as history.) Rules, in order, each failure a typed `ContractError` naming the contract, member and rule (never a panic):

1. Closed objects and exact member types, patterns, enums, ranges and array rules as in the schemas, plus the schemas' conditional requirements (class and trust, registered command for mechanical evaluators, `revoked_at` exactly when revoked, `attestation_ref` for trust M).
2. Every timestamp parses with the kernel's strict rules (`Timestamp::parse_strict`: `YYYY-MM-DDTHH:MM:SSZ` of a real calendar time; no day 30 of February, month 13 or hour 24).
3. `canonical_target` is a canonical resource id per the kernel (`is_canonical_resource_id`: no empty, `.` or `..` segment) and equals `workflow:<tenant_id>/<project_id>/<workflow_id>` of the same document (a target for another tenant, project or workflow is refused). The schema pattern now also rejects `.` and `..` segments structurally.
4. Temporal order: `started_at <= finished_at <= fresh_until` (attestation), `issued_at <= fresh_until` (record), `revoked_at >= published_at` (registry entry); observations are not in the future relative to a trusted `now` passed in explicitly: `finished_at <= now`, `issued_at <= now`.

Not covered by `broker::contracts` (still M3-05 and M3-07): MAC verification, registry lookup, binding equality against the protected transition at use time, freshness against trusted effective time at use, and consumption.

**Negative tests (schema level, passing):** unknown members at every level; every context and evaluator binding missing; attestation without command, inputs, output, exit status, purpose, auth, id or freshness; unknown or wrongly cased algorithms; malformed tags; wrong purpose; missing or global scope; mechanical without a registered command or with trust MA; revoked without `revoked_at` and active with one; empty criteria; uppercase digests, fractional or offset times, out-of-range exit status and revisions, malformed targets, empty inputs, invalid criterion ids; mechanical evaluation without an attestation; unknown mode. **Semantic negative tests (Rust, `broker::contracts`, passing):** `..` and `.` target segments and other invalid target structure; a target for another tenant, project or workflow; impossible calendar times (`2026-02-30`, month 13, hour 24, minute or second 60, non-leap 29 February); inverted execution interval; `fresh_until` before `finished_at` or `issued_at`; future `finished_at` or `issued_at`; `revoked_at` before `published_at`. Use-time semantic negative tests (binding mismatch against the transition, registry mismatch, revoked evaluator, replayed attestation, stale freshness, snapshot mismatch) are written with M3-05 and M3-07.

## Authenticated AcceptanceRecord contract (D-036 item 1, implemented in `broker::acceptance`)

`authenticated-acceptance-record/1` is a closed object: `contract_version`; `purpose` `writ.acceptance-record.v1`; `issuer` (acceptance service id); `mode` (`governed` or `advisory`); `record` (the kernel AcceptanceRecord contract, unchanged, including its unkeyed `record_digest`); `evaluations` (one per record criterion: `criterion_id`, `evaluation_id`, `evaluator_id` equal to the criterion's, `evaluator_version`, `implementation_digest`, `environment_digest`, `registry_revision`, `attestation_id` (required exactly when the criterion's trust is `M`, otherwise `null`), `evidence_digests`); `auth` (`alg` `hmac-sha256`, `key_id`, `mac` as 64 hex digits).

- **MAC bytes:** UTF-8 of the D-006 canonical JSON of the whole document with only `auth.mac` removed; every other member, including `issuer`, `mode`, all of `record`, all evaluations and `auth.alg`/`auth.key_id`, is authenticated.
- **Key:** an `AcceptanceRecordKey` (its own type and purpose, never usable as an ingress, permit or runner key); unknown, revoked or wrong-purpose keys refuse (`ACCEPTANCE_RECORD_UNAUTHENTICATED`), an unavailable key ring fails closed (`ACCEPTANCE_KEY_UNAVAILABLE`).
- **Projection:** after the MAC verifies, the `record` member alone goes to the kernel contract; the evaluations are checked against it; `advisory` refuses (`ACCEPTANCE_ADVISORY`).
- A valid MAC authenticates the issuer only; current-policy, registry, revocation, freshness, immutable-snapshot and acceptance checks still run at use time. Production key provisioning and the acceptance service are future obligations.

## Mechanical runner (M3-07, implemented in `broker::runner`, `broker::process`, `writ_ledger_sqlite::SqliteRunnerStore`)

**Effect path:** a runner evaluation is a broker effect of kind `runner.evaluate` through the execute lifecycle (reserve, dispatch, permit, T-adapter, observe). The request supplies names only (exactly the attributes `workflow_id`, `from_state`, `to_state`, `criterion_id`, `acceptance_record_id`, `evaluator_id`; resource `workflow:<tenant>/<project>/<workflow>`; no capabilities). Everything the attestation binds is read from trusted state at run time: stored workflow (task, state, revision, snapshot id and digest), the active acceptance policy, the current registry entry, the registered command, the immutable snapshot content and the runner key named by the registry entry's `attestation.key_id`. The runner store (`writ-runner-1`, separate file, same identity, ownership lock and ledger binding as the effect store) records the permit as consumed with state `started` in one committed transaction before anything runs, then `applied` with the attestation or `failed` with an operator diagnostic. A `started` run is never run again and is not completion evidence: the receipt stays uncertain (`unknown_reconcile`) with no automatic resolution (D-035 item 3); a failure to record the outcome is reported with `outcome_unknown`. The attestation id is `att-<permit id>`.

**Formats (implementation choices within D-033/D-036):** command digest: D-006 digest of `{"contract":"writ-command/1","command_id","program_digest","args","env"}` (`program_digest` the SHA-256 of the executable bytes, `env` sorted `[name, value]` pairs; empty, duplicate, `=`- or NUL-containing names make the digest undefined and the command unusable). Snapshot digest: D-006 digest of `{"contract":"writ-snapshot-manifest/1","files":[{"path","digest"}]}` sorted by path (relative `/`-separated paths without empty, `.` or `..` components). Output digest: D-006 digest of `{"contract":"writ-runner-output/1","exit_status","stdout","stderr"}` with SHA-256 digests of the captured bytes. Sandbox environment digest: D-006 digest of `{"contract":"writ-sandbox-profile/1","profile","guarantees"}`; it must equal the registry entry's `environment_digest`. A `#!` script's interpreter is not covered by the command digest.

**Fail closed:** the runner runs nothing unless the sandbox reports every guarantee in `RunnerRequirements`. The supported configuration (`RunnerRequirements::production`) requires filesystem and network isolation, process-tree containment, resource limits, closed descriptors and bounded execution; **no M3 sandbox provides them, so production configuration refuses every job until a contained sandbox exists (M5).** The only M3 sandbox, `LocalProcessSandbox` (profile `local-process-uncontained/1`), provides bounded execution (wall-time kill, output cap, cleared environment, null stdin, always reaped) and closed descriptors (checked through `/proc/self/fdinfo` before each job; spawns go through the process lifecycle gate) and nothing else: its jobs run with the broker's full user privileges. It is accepted only by `RunnerRequirements::uncontained_for_disposable_tests`, which is compiled only in test builds (feature `uncontained-test-runner`, enabled solely by a dev-dependency). A snapshot store that does not report `immutable()` gives `ARTIFACT_INTEGRITY_UNAVAILABLE`; snapshot and program bytes are materialized into a fresh private directory and re-verified by digest before the run.

**Process lifecycle (E-066, D-035 item 6):** acquiring and releasing every `.owner` lock happens under the exclusive guard of a process-wide lifecycle gate, every production spawn under its shared guard, and ownership locks are unlocked before close (a `flock` lock belongs to the open file description, so a child's not-yet-closed duplicate cannot keep a released lock alive). The gate alone was insufficient (stress test failed 3 of 5 runs without unlock-before-close); with both, the reopen-while-spawning stress test passes.

**Host precondition (E-071):** the broker process must start without any descriptor above 2 that lacks close-on-exec; otherwise `LocalProcessSandbox` reports `descriptors_closed` false and the runner refuses every job (fail closed; such a descriptor cannot be closed in the child without `unsafe` code). `m3/tools/run-with-clean-fds.sh` establishes this for tests and CI.

**Known limitations (not production guarantees):** descendants of a job are not contained (direct-child kill only; a process-group kill needs a dependency decision); a job holds the shared policy gate and the workflow lock for its whole wall time (administration, activation, reconciliation and promotions of that workflow wait); reconciliation reads both stores, so either store's outage blocks reconciliation of every receipt; work directories of a crashed broker are not swept and a cleanup failure is not reported; the runner reads snapshot bytes through `SnapshotContent` while promotion and administration use `SnapshotStore::check`: they must be one service-controlled store using the manifest digest, which does not exist yet (INV-40); runner key management is test-only (M5, M9).
