# Trusted time for the broker (risk 14): revised design for owner review

**Status:** REVISION 2 (2026-11-12), direction approved by the owner (D-033 item 3), mechanism revised per the owner's corrections; approved for the documented local profile and **implemented** in `writ-broker` (`broker/src/clock.rs`) and `writ-ledger-sqlite` (schema `writ-ledger-2`) on 2026-11-12 (see "Implementation" below). ADR-0008 APPROVED IN PRINCIPLE; release and production NO-GO.

**Requirement:** the agent never supplies authoritative time. While the broker runs, no clock fault (wall-clock rollback, forward jump, skew, suspend) can extend the lifetime of a grant, permit, deadline, reservation or acceptance record, and a detected anomaly never extends one either. Across downtime (restart, owner change) the design cannot measure elapsed time: lifetimes are protected against detected rollbacks (more than 120 s below the persisted high-water mark fails closed), but an undetected backward step of the host clock during downtime can extend them by up to that step, so this part depends on host-clock integrity (see "Residual risk"; not solved here). Where trustworthy expiry cannot be established, time-sensitive operations fail closed.

## Why revision 1 was insufficient

`effective_now = max(clock_now, high_water)` freezes effective time while the wall clock is behind the watermark: during a rollback every lifetime stops advancing, which **extends** it. Comparing a forward jump only against the persisted watermark also misreads ordinary downtime (a broker stopped for two days) as a jump.

## Mechanism

1. **Effective time comes from elapsed time, not from the wall clock.** At start the broker fixes a base `B` (rule 3) and a monotonic anchor; while it runs, `effective_now = B + elapsed`, where `elapsed` is read from a monotonic clock that **keeps counting during system suspend** (Linux `CLOCK_BOOTTIME`). Lifetimes therefore keep running through wall-clock rollbacks and through suspend; the wall clock never moves effective time backward or forward while the broker runs.
2. **The wall clock is only a detector while running:** `drift = wall_now - effective_now`. `drift < -120 s` is a rollback diagnostic; `drift > +24 h` is a forward-jump diagnostic (measured against the elapsed-time baseline, not the watermark, so downtime is never involved while running). Diagnostics are operator records; neither changes `effective_now`, so a detected rollback cannot pause or extend anything. 120 s and 24 h are diagnostic thresholds, never allowances.
3. **Startup and restart** (no elapsed baseline exists across downtime): read the persisted high-water mark `H` and the wall clock `W0`.
   - `W0 >= H`: `B = W0` (downtime of any length is normal; a wall clock that ran ahead during downtime only expires things earlier, fail closed).
   - `H - 120 s <= W0 < H`: `B = H` (small rollback across downtime absorbed; lifetimes then run from `H`).
   - `W0 < H - 120 s`: **fail closed** for every time-sensitive operation until an authenticated, authorized, audited operator acknowledgement; the acknowledgement starts the broker with `B = H` (never lower), so it cannot revive anything that had expired at `H`.
4. **Persisted floor:** the effective time used to decide an expiry (or any time-sensitive refusal) is written to the high-water mark in its **own fenced transaction before** the governed operation's result is final, so it persists even when the governed operation is refused or rolled back. The mark is also written periodically while running and is never lowered (fenced, owner-checked, D-029 and M3-01 ownership).
5. **Owner changes:** a new owner reads the same persisted `H` (single-owner ledger), so rule 3 applies unchanged.
6. **Acknowledgement:** an operator action through an authenticated, authorized channel (not the agent, not a model, not a request field), recorded in the audit log; it can only allow starting from `H`; it never lowers `H`, never revives expired or revoked credentials, and there is no silent reset.

## Residual risk (documented, not solved here)

Across downtime there is no elapsed baseline: if the host clock is moved backward during downtime by less than the downtime itself, the restart sees `W0 >= H` and cannot detect it, so lifetimes that should have ended during downtime can appear to end later than intended by up to that amount. Security therefore still depends on host-clock integrity across downtime (trusted time synchronization, agent unable to set the clock); real-host clock security is M5 and is not resolved by this design.

## Suspend-aware monotonic clock (decided)

Rule 1 needs `CLOCK_BOOTTIME`; `std::time::Instant` on Linux is not documented to count suspend. The owner chose option 1 on 2026-11-12: `rustix` `=1.1.6` (`default-features = false`, feature `time`), reviewed in `broker/DEPENDENCIES.md`; `unsafe_code` stays forbidden. The rejected alternatives were a documented `unsafe` exception for `libc` and treating suspend as unsupported.

## Implementation (2026-11-12)

- **Fallible time.** `TrustedClock::now` returns `Result<Timestamp, ClockError>`. Clock-source failures, a regressing elapsed clock, arithmetic overflow or a time outside the kernel's range (years 0000 to 9999), an unacknowledged startup rollback, a persisted floor later than the reading, and any failure to read, raise or audit the floor are `ClockError`s, refused as internal `TIME_UNAVAILABLE` (externally the kernel's generic `PROMOTION_REFUSED`; permit issue fails with `PermitIssueError::TimeUnavailable`). There is no fallback to zero, a cached value or the plain wall clock. `FixedClock` (tests and harnesses) can inject failures.
- **`HostClock`** (local profile): effective time is `base + elapsed` in nanoseconds, elapsed from `Boottime` (`clock_gettime_dynamic(DynamicClockId::Boottime)`), wall clock from `SystemWall` (`std::time::SystemTime`), both behind the `ElapsedSource` and `WallSource` traits so tests inject readings. A failing wall read while running also fails closed, although the wall clock is only a detector.
- **Drift diagnostics:** `drift = wall - effective`; `< -120 s` is `rollback_detected`, `> +24 h` is `forward_jump_detected`, a return within the thresholds is `drift_normal`. A change of drift is recorded once as a clock event (not on every read); effective time never changes.
- **Startup** (`HostClock::start`): rule 3 exactly (`W0 >= H` or no `H`: base `W0`; `H - 120 s <= W0 < H`: base `H`; below: blocked); the outcome is recorded as a clock event, and a running start raises the floor to its base.
- **Acknowledgement** (`HostClock::acknowledge`): only on a blocked clock (otherwise `NotBlocked`; no silent reset); an `OperatorAuthority` must authenticate and authorize it (`Unauthenticated`, `Unauthorized`); it must name the persisted `H` (otherwise `Stale`, so an acknowledgement cannot be replayed against a later condition). Every attempt is recorded in the ledger with the operator identity when authenticated; success starts the clock from `H`, never lowers `H` and never revives anything expired at `H`. There is no production `OperatorAuthority` yet (the operator channel is later work), so in production a blocked startup stays blocked. The acknowledgement is not a request field and is unreachable from agent input.
- **Persisted floor:** a time-sensitive decision takes its time from `clock::observe`, which reads the clock and raises the ledger floor in its own fenced `time_floor` transaction before returning an `ObservedTime` (a `TrustedClock` fixed at that instant). The floor is therefore durable before the decision's result is final, whatever happens to the governed operation afterwards. The floor is written on every observation; a separate periodic timer is not implemented (the broker has no runtime loop yet).
- **Ledger (`writ-ledger-2`):** table `time_floor` (at most one row, `floor_s`, `floor_ns`), raised by `LedgerStore::raise_time_floor` with `ON CONFLICT ... WHERE (new) > (stored)` and returning the stored maximum; table `clock_events` (closed set of kinds; effective, wall, floor, operator). Both are covered by the exact-schema verification; `writ-ledger-1` ledgers are refused (nothing is deployed).

## Tests

Implemented and run on 2026-11-12 (`cargo test --workspace --locked`): suspend (wall and elapsed both jump) keeps lifetimes running; rollback while running neither pauses nor extends a permit and is recorded once; forward jump is reported without changing effective time; an expiry observation persists despite a refused governed operation, a failed audit transaction (injected at begin, body and commit on SQLite) and a restart with the clock set back (absorbed within 120 s, fail closed beyond); long downtime is accepted; a large backward step at startup fails closed; unauthenticated, unauthorized and stale acknowledgements are refused and recorded; an acknowledgement starts from `H` without reviving an expired permit; the floor is never lowered by any operation; clock-source, overflow and floor failures give `TIME_UNAVAILABLE`; a real `CLOCK_BOOTTIME` smoke test (two reads, non-decreasing; no suspend, no clock change). Not covered yet: owner change after a rollback (needs the multi-process ownership harness with a clock), grants and reservations (not implemented), agent-supplied time (no request field carries authoritative time; covered by the existing use-time decision tests only).
