# Isolated containment CI (M5a-12, D-047)

**BLOCKED.** [workflow.yml](workflow.yml) is a draft for a private, owner-controlled CI repository with a restricted runner group and a host-side provisioner. The [guest wrapper and required-result manifest](GUEST-GATE.md) and [host lifecycle controller](HOST-CONTROL.md) are available for offline review. The live matrix driver, infrastructure adapters, deployed watchdog and dedicated required status are outstanding. The six existing required jobs remain in place. The [reference-VM checklist](../../docs/implementation/M5A-GATE-REVIEW.md#4-verify-in-vm-checklist-all-open) stays open.

## Admission

1. Configure a private control repository owned by an organization with workflow-level runner-group controls, a protected default branch and owner-controlled dispatch. Install the reviewed draft as `.github/workflows/writ-containment.yml` there. Configure the `writ-containment` runner group to allow only that repository and the exact workflow path and protected branch. Restrict access to the workflow, its variables and the runner group. Keep Writ's public repository outside the runner group. Verify actual repository and selected-workflow restrictions, public access disabled, and the protected-ref policy. Pin the control revision in the admission record.
2. Maintain a host-side approval record binding the fixed upstream repository, `refs/heads/v2/architecture-rebuild`, the full Writ SHA, approved test manifest and control workflow revision. Require review of the exact commit, including build scripts, dependencies, privileged setup, test code and workflow. A dispatch input, matching label, or green ordinary CI cannot supply that approval.
3. Admit a queued job only after independently authenticating its GitHub API record on the host. Check the private repo, dispatch event, workflow revision and protected ref, job name, run ID, attempt, label and single-use approval. Fetch the fixed upstream ref on the host, verify the approved SHA belongs to it and stage that exact Git tree without credentials. Bind the input to the trusted dispatch record and independently authorize each attempt. Persist a lifecycle record before acquiring any guest or runner resource, then reconcile pending lifecycle records on restart. Apply a queue deadline on the host and cancel the run on refusal, timeout or provisioning failure. Fail the external status if the job could not run.
4. Enable `WRIT_CONTAINMENT_PROVISIONER_READY=1` only after the owner has provisioned and tested this control path, including deliberate missing-runner and cancellation cases. The hosted preflight currently fails with the infrastructure blocker when the flag is unset. Its result alone cannot satisfy M5a-12.

## Single-job guest and evidence

1. Create a fresh Ubuntu 24.04 guest from a verified, clean CI base and a unique overlay. Use a separate base or a pristine pretrial base, with no shared host filesystem, credential directory, agent socket or reference-trial disk. Keep hypervisor credentials, GitHub App credentials and status publishing on the host. Restrict guest networking to necessary CI and package endpoints, with private workstation, control-plane, metadata and production networks unreachable. Provision dependencies and source before the privileged test when possible.
2. The owner designates the disposable CI guest before tests. Use a dedicated unprivileged runner user and a constrained privileged entry point. Bake a root-owned, runner-immutable `/opt/writ-ci/bin/run-containment` into the CI base only after its review. It must validate the VM/profile and marker, verify the staged tree against the reviewed source manifest, run the required automated containment matrix and negative controls, and fail for missing, inconclusive or skipped required results. Keep the full reference checklist and its separate evidence obligation. A wrapper that only runs `trial.sh` or ordinary CI is insufficient.
3. Use a short-lived, single-job registration mechanism such as GitHub's just-in-time runner configuration. Bind it to the restricted group and run/attempt label. Inject it directly into the guest at boot without logging or persisting it in the base. Register no general-purpose runner. The draft uses no Git checkout step and requests no GitHub API permissions. Give the guest no additional checkout, personal, model or production credentials.
4. Keep the VM lifecycle deadline external to Actions. On success, failure, cancellation or timeout, stop the guest and extract only a bounded, schema-validated evidence record over a one-way export or from the stopped overlay in an isolated reader. Allow-list fields such as test IDs and outcomes, source and image hashes, versions and timing. Exclude free-form output, environment, configuration and raw journals from publication. Treat guest evidence as untrusted input. Record missing or malformed evidence as failure. Have the host compare the exact required evidence set with its approved manifest and bind the evidence to the run ID, attempt and one-time host challenge. Guest output alone cannot attest to resistance to guest-root or hypervisor compromise. Preserve the admitted identity, approved manifest digest and guest destruction outcome in the host-side record.
5. Deregister any remaining runner, revoke unused registration material and destroy the disk and guest on every exit path. Keep a host-side cleanup watchdog for orchestrator outages. Publish the dedicated required status on the original Writ SHA from a restricted host-side GitHub App only after authenticating the exact admitted job and attempt with terminal success from the GitHub API, validating evidence and confirming cleanup. Fence status publication per SHA so an old or cancelled attempt cannot overwrite a newer authoritative outcome. Failure to destroy or validate is a failed gate. Pin the status to that App when configuring branch protection. Confirm a failed or absent required result blocks the gate, and that ordinary CI cannot stand in for it.

The owner must supply the private control repository, runner-group restriction, hypervisor access, host-side provisioner and narrowly scoped App. Review and install the completed control path only after the live matrix driver, host adapters and watchdog have been implemented and tested. Then verify it end to end on the isolated runner. Until then, leave the draft outside the active workflows and keep M5a-12 blocked.
