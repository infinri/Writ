# Development MCP shim (M5b-02, M5b-03)

Build the Linux executable with `cargo build --locked -p writ-mcp-shim`. Start it as an MCP subprocess with piped stdin and stdout. It negotiates MCP 2025-11-25 through rmcp, and presents an empty tool list while governed activation is unavailable. A direct attempt to use a valid effect proposal is refused. The executable has no live RPC endpoint configuration.

The same handlers and SDK transport run in `cargo test --locked -p writ-mcp-shim` with an authenticated recording Unix RPC peer. They list one tool, `fs.write`, and accept create-only snapshot proposals with exactly six strings: `relative_path`, `source_path`, `snapshot_id`, `manifest_digest`, `content_digest` and `idempotency_key`. The peer receives one J-2 control frame for each accepted effect-bearing call. It records the reserved `effect.request` operation, action `fs.write`, mode `create_only` and the six fields. No client value establishes tenant, project, identity, approval, authorization or time. The recorded receipt describes a submission. Writ's service and broker must still authorize and carry out any real effect. Current `writ-serviced` refuses `effect.request`, and the recording peer performs no effects.

Admission follows SDK typed receive order per connection. Duplicate initialization, duplicate initialized notifications and duplicate pending request IDs close the connection. Canceled IDs remain reserved for the connection so a delayed callback cannot acquire a later request's admission. The shim follows the SDK's behavior for malformed or oversized lines it handles internally. Typed receive EOF revokes pending admission before SDK draining starts. Cancellation and disconnect can prevent the first write. Once any bytes were sent, a subsequent failure may leave an uncertain outcome. The shim never reconnects or replays a submitted request. The SDK can suppress a canceled call's response.

These tests demonstrate development wire and forwarding behavior. Real effect ingress, broker composition, containment, owner-designated VM evidence and isolated containment CI remain open. Enabling a live backend requires verified M5a foundations. [Owner decision and dependency review](../../docs/implementation/m5-deps/d047-rmcp-review.md#d-049-final-adoption-review)
