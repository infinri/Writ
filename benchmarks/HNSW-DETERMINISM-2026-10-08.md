## Follow-up F4: single-threaded HNSW insertion

BEFORE is HEAD (`add_items` with the library's default thread count); AFTER passes
`num_threads=1` in `HnswlibStore.build_index`. All four `measure` runs were taken in one
hold of the shared test-graph lock against the isolated graph, freshly loaded from
writ-corpus.cypher, each with its own empty HNSW cache directory (the driver patched
`writ.retrieval.pipeline.get_hnsw_cache_dir`; the shared cache was not touched). The table
above compares BEFORE-1 with AFTER-1. Every rule ranking metric is equal before and after,
in both arms and every pool, so no AFTER interval is disjoint from and below its BEFORE
interval.

Determinism of the rule index (317 indexed vectors, 384 dimensions):

| pair | saved index bytes (`bin_sha256`) | `recorded` sections | queries that differ |
|---|---|---|---|
| BEFORE-1 vs BEFORE-2 | differ (`f2bde1a3...` vs `fd16d7c4...`) | differ | 4 gold, 4 negatives (ranks 5 to 10) |
| AFTER-1 vs AFTER-2 | equal (`47ef3867...`) | differ | 2 gold (ranks 3 and 4, 9 and 10) |
| AFTER, `PYTHONHASHSEED=0`, run 1 vs run 2 | equal (`47ef3867...`) | equal | none |

The change makes the index itself reproducible: both AFTER builds saved byte-identical
files, and both BEFORE builds did not. It does not make the `recorded` sections equal on
its own. The two AFTER differences are adjacent pairs swapping places (positions 3 and 4 in
one query, 9 and 10 in the other) with the same abstain signal, and they disappear when
both runs use the same string hash seed: the remaining variation is the order of tied
scores, which follows Python's per-process hash randomization in the ranking stage, not the
HNSW build. No metric moves with it (the scored arms are equal in every pair above). Making
tie order reproducible is a ranking change outside this item.

Build-time cost (`HnswlibStore.build_index` on seeded unit vectors at 384 dimensions,
ef_construction 200, M 16, median of five builds, 16 logical cores):

| vectors | default threads | one thread |
|---|---|---|
| 317 (the rule corpus) | 0.008 s | 0.014 s |
| 10,000 | 0.63 s | 3.83 s |

The cost is paid only when the index is rebuilt on a cache miss, beside a full encode pass
of the same corpus. An index already cached on disk keeps loading on a corpus-hash hit, so
production reaches the deterministic build at its next cache miss.
