# writ-approval dependencies (D-041, D-042)

Human approval channel (M4): WebAuthn passkey verifier (`webauthn-rs` 0.6.2, default features off, `danger-allow-state-serialisation` for ceremony state held only in the ledger) and the loopback HTTP/1 approval listener (`hyper` 1, `server` and `http1` only; `hyper-util` with `tokio`; `tokio` with `rt`, `net`, `time`). Dev only: `webauthn-authenticator-rs` 0.6.2 (`softpasskey`), never shipped.

- Allow-list: [`deps-allowlist.json`](deps-allowlist.json), generated by [`allowlist.py`](../docs/implementation/m4-deps-lead/allowlist.py) from the reviewed lock: exact version and checksum per package; `name@version` keys where two versions coexist; licences outside the general set carry their decision (D-041 DR-2, D-042 DR-5); `locked_unbuilt` records lock entries no supported build compiles; `forbidden` and `forbidden_features` keep TLS stacks, OpenSSL, SQLite, HTTP/2 and client features out.
- Review and reproduction: [M4-DEPENDENCY-REVIEW](../docs/implementation/M4-DEPENDENCY-REVIEW.md); notices: [THIRD-PARTY-NOTICES](../THIRD-PARTY-NOTICES.md).
- Advisory: `rsa` 0.10.0-rc.19 (RUSTSEC-2023-0071) under a DEVELOPMENT-ONLY exception (D-041 DR-3), visible in every gate run; `check_deps.py --release` fails on it. Release needs an explicit disposition.
- Tokio and Hyper stay out of the `writ-kernel`, `writ-broker` and `writ-ledger-sqlite` standalone closures (the broker allow-list forbids `tokio`); they appear in the combined application graph, which the gate reports.
- Upstream concentration (`crypto-glue`, single maintainer) is a tracked risk (D-041 DR-4); replacement boundary: the broker-owned `HumanVerifier` trait. Update procedure: change the pin, regenerate the allow-list, repeat the review (licences, OSV, closures, age, checksums) and record it before merging.
